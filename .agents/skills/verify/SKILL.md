# Verify your change in Omni OS

Get yourself into a loop: change, run, look, fix, until the change provably works. Do not hand the user something you have not seen working. Pick the steps that fit the change; this is a checklist, not a script.

## 1. Static checks (every change)

- `npm run typecheck`
- `npm test` (turbo boundaries, then every package's vitest), or one package: `npx turbo run test --filter=@omni/<server|web|desktop|shared>`, or one file while iterating: `cd apps/server && npx vitest run tests/<file>.test.ts` (each package has its own `vitest.config.ts`).
- A failing test: rerun it on `main` in a separate worktree (`git worktree add <scratch>/main main`, `npm install --include=dev` there, then `npx vitest run ...`) before treating it as yours. Never stash or check out in this one: the stash is shared with other worktrees. Apart from the known blockers below, the suite passes on macOS and Linux, so a failure that main does not show is yours.
- `npm run build` for web changes. Run it alone, not chained after other commands.
- Desktop app: `cd apps/desktop && npx vitest run && npx tsc --noEmit`.

## 2. Run it

`scripts/qa-stack.sh up` starts a throwaway server (:4757) with its own data dir and the fake CLIs, vite in front (:4768), and seeds sample threads. It prints the thread URLs. `QA_SERVER_PORT=<port> scripts/qa-stack.sh down` stops it and deletes its data. `down` refuses to run without the port, and refuses a stack whose processes run from another checkout, so it cannot stop another thread's stack. Never test against :4747 or `data/`: that is the live workspace.

- Threads run on `packages/test-fixtures/fake-claude.mjs`. Drive a turn with directives in the prompt: `RICH` (tools, plan, sub-agent), `TOOL:<ms>`, `BG:<ms>`, `LIMIT[:<epoch>]`, `CTX:<tokens>`, `PUBLISH:<path>`, and more listed at the top of that file.
- Every `/api` call needs the stack's own token (`status` prints it; it is `$QA_DIR/data/api-token`, default `$TMPDIR/omni-qa-<port>/data/api-token`). Your shell's `OMNI_TOKEN` is the live server's, so never use it here. `T=$(cat "${TMPDIR:-/tmp}/omni-qa-4757/data/api-token")`
- Create a thread: `curl -s -X POST localhost:4757/api/threads -H "Authorization: Bearer $T" -H 'content-type: application/json' -d '{"channel":"inbox","prompt":"RICH"}'`
- The web URLs `up` and `status` print end in `?pair=<token>`, which pairs the browser. A bare URL shows the pairing screen.
- A plain fake turn ends in about 30 ms, too fast to watch a working state. Start the stack with `FAKE_CLAUDE_LATENCY_MS=1500` in its environment for turns that last a few seconds.
- A channel's PR pages: `qa-stack.sh` does not put `fake-gh.mjs` on the server's PATH, so the server runs your real `gh` against GitHub and a fixture repo fails ("Could not resolve to a Repository"). Add `$QA_DIR/bin/gh` with `exec node <worktree>/packages/test-fixtures/fake-gh.mjs "$@"`, then give a channel `"github_repo": "acme/shop"` (its PRs are #12, #9 and #7).
- A real PR's page (its body, diff and checks): a `$QA_DIR/bin/gh` stub that passes only read calls (`pr view`, `pr diff`, `pr list`, `repo view`) to the real gh and refuses the rest, so no slide or button can merge it. Exec the real binary (`~/.local/share/mise/installs/gh/latest/*/bin/gh` on omarchy), not `~/.local/bin/gh`: that mise wrapper finds the stub first on PATH and the two call each other forever. Give a thread the PR's head branch (and a `parent_id`) in the QA db to fill the page's thread links.
- A PR on a thread's branch: `fake-gh.mjs` ignores `--head`, so `pr list` hands every thread the same fixture PRs. Put a small `gh` script in `$QA_DIR/bin` (first on the server's PATH, read at each call) that answers `pr list --head <branch>` with the PR you need and passes everything else to `fake-gh.mjs`.
- A machine picker (Run automations on, an automation's Machine, the composer's Machine chip) is off until sync is armed. On a QA stack, write kv `sync.machine_id` (this machine) and `devices.<id>` records (`{id, name, tailscale: null, at}`) for it and a fake second machine into `$QA_DIR/data/omni.db`, then restart only the stack's server by its PID with the same environment (`/proc/<pid>/environ` on Linux): the id is read at boot. No relay is needed.
- Need some other state (folders, channels, a stuck request)? Build it through the API first; reach into the sqlite db in the QA data dir only when no route exists.
- Timing a path on real data (a slow thread, a big list): copy the live db read-only, `sqlite3 -readonly data/omni.db ".backup '<scratch>/data/omni.db'"`, then in the copy `update kv set value='false' where key='sync.enabled'` and set `running`/`queued` threads to `done`, and start the server on it with a `security` stub that exits 44 (no Keychain, so no relay token) and a `gh` stub. `app.request()` from `apps/server/app.ts` times a route in-process without listening. A phone's link is not loopback: put a proxy with latency and a shared bandwidth cap between the client and the server, or a request that queues behind a big download looks instant.

## 3. Drive it

- Web: open the printed URL in a browser tool (the thread's `omni-browser` MCP, Claude in Chrome, or Playwright). Click through the actual flow you changed, not just the page load. Check desktop width and 390px phone width (the phone layout is its own code in `apps/web/src/mobile/`), and dark mode (`browser_emulate_media`) when colour changed.
- With `omni-browser`, take a `browser_snapshot` before clicking. Pass the exact snapshot reference as `target` to `browser_click`; `element` is only a description, and `ref` is not a supported argument. For a selector, pass a valid unique CSS selector as `target`.
- Omit the `omni-browser` screenshot filename to save in the thread's browser folder. An explicit relative filename saves in the working directory instead. Do not pass an absolute path in `/tmp` or another directory outside the thread's browser folder and worktree. Read or copy the exact returned path, then put a copy in `shots/` for `scripts/pr-screenshots.sh`.
- Server: curl the route and read the response. Then check the side effect: the row in the QA db, the feed event (`curl -N localhost:4757/api/feed`), the line in `scripts/qa-stack.sh logs`.
- Desktop app: `cd apps/desktop && npx tsx scripts/qa.ts --script run.json --out <scratch>/qa` launches the Electron app with Playwright, attaches it to the stack (`"port"` and `"dataDir"` in the script, the stack's `$QA_DIR/data`), runs the steps and writes PNGs and `qa.json`. It exits non-zero on a failed step and refuses :4747 and a checkout's `data/`. The steps and flags are under "QA harness" in `apps/desktop/README.md`. Add `--app-url http://127.0.0.1:<vite port>` with a Vite on `127.0.0.1` in front of the stack to see a Web UI change (`OMNI_PORT=<server port> npx vite --config apps/web/vite.config.ts --host 127.0.0.1 --port <free port> --strictPort`; the stack's own vite may listen on `::1` only); the server alone serves the last build of `apps/web/dist`. `--app <path>` runs a packaged build instead of the dev one.

## 4. Prove it

- Visible change: before (from `main`) and after screenshots, attached as `docs/pr-screenshots.md` says.
- Backend change: the request and response, or the log line that shows the new path ran. When nothing proves the path ran, add a log line.
- Put what you ran under a `Verified:` line in your reply and PR body, and what you could not run under `Not verified:`. Never claim a check you did not run.

## 5. When you get blocked, fix this skill

If something stopped you (a missing env var, a crash on boot, a step here that is wrong), solve it, then edit this file so the next run does not hit it. Keep the fix short and in the right section. Commit it with your change.

Known blockers:
- An Omni thread's shell sets `OMNI_DATA_DIR` to the live `data/`, so `npx vitest run` there writes test threads into the live workspace and reads its config (`OMNI_USER` comes out as Ben and `toEqual` checks fail). Run tests with `env -u OMNI_DATA_DIR -u OMNI_URL -u OMNI_THREAD_ID -u OMNI_TOKEN -u OMNI_TOKEN_FILE`.
- A worktree whose `node_modules` was stripped has no `node_modules/.bin/tsx`, so every test that spawns the conductor's MCP server (`automation-tools-mcp`) times out. `npm ci --include=dev` restores it.
- macOS has no `setsid`; `qa-stack.sh` falls back to perl's `setpgrp`. The PID file holds the subshell, so `down` stops the group its child leads.
- A Vite you started with `npx vite ... &` runs as a child of `npx`: killing the `$!` PID leaves the child holding the port. Stop the PID `ss -ltnp | grep :<port>` shows (check its `/proc/<pid>/cwd` is yours first). For `main` before shots, `git worktree add --detach <scratch>/main main`, symlink each `apps/*` and `packages/*` `node_modules` into it, hard-link the root one (`cp -al <worktree>/node_modules <scratch>/main/`, same filesystem) and start its Vite with `--force` against the same QA server. A symlinked root `node_modules` resolves outside that checkout, so Vite answers 403 for the fonts and the before shots fall back to another font.
- A Linux box may have no `lsof`: `qa-stack.sh` reads a process's cwd from `/proc` instead, and `ss -ltnp | grep :<port>` stands in for `lsof -iTCP:<port>` in the checks below.
- Another worktree's QA stack can already hold :4757 (`up` then logs "port 4757 ... is in use" and your curls hit the wrong code). Check `lsof -nP -iTCP:4757 -sTCP:LISTEN` and move with `QA_SERVER_PORT`/`QA_WEB_PORT`.
- With several agents running, 4757/4768 and the obvious pairs (4791, 4801, 4811, 4893, 4917, 5131) are often all taken. Find a free pair first: `for p in 6231 6331 6431 6531; do lsof -nP -iTCP:$p -sTCP:LISTEN >/dev/null || lsof -nP -iTCP:$((p+1)) -sTCP:LISTEN >/dev/null || { echo $p; break; }; done`, then pass it as `QA_SERVER_PORT`/`QA_WEB_PORT`.
- `qa-stack.sh up` without a working `cargo` on PATH starts with no `omni-mcp`, so the fake CLI's `RENDER`, `STEPS` and `ASK` do nothing and no html_render frame reaches a transcript. On omarchy the mise shim has no Rust version: run `up` with `PATH="$HOME/.cargo/bin:$PATH"`.
- CSP checks (the Web UI shell's policy, `apps/server/web-headers.ts`): browse the stack's server port, not Vite, which sends no headers. A violation shows as an INFO console line ("violates the following Content Security Policy directive") and in `GET /api/csp-report` (token). The desktop harness lists them in `qa.json` `cspViolations`, but only for windows opened after launch (`openWindow`, `openThread`): the first window loads before it listens. Prove a zero with a control first, such as an inline `onload` on `<body>` in `apps/web/dist/index.html` (ignored build output; restore it after). Chromium and Electron never delivered `report-to` reports to http://127.0.0.1 in tests, so the shell uses `report-uri`.
- A live turn needs the real CLI: `QA_CLAUDE_BIN=$(which claude) QA_CODEX_BIN=$(which codex) QA_CURSOR_BIN=$(which cursor-agent) scripts/qa-stack.sh up --seed 0` swaps any of the fakes, and spends that plan. Cursor's dashboard calls (`harness/cursor/dashboard.ts`) run on a QA stack by default and are off in vitest (`OMNI_CURSOR_DASHBOARD=0`).
- `up` can print "up" for both ports while another worktree's stack holds them, so the browser shows that worktree's code. After `up`, check `lsof -t -iTCP:<web port> -sTCP:LISTEN | xargs -I{} lsof -p {} | grep cwd` points at your worktree.
- A thread's fake CLI stays alive after its turn (and after `/stop`), so the next message skips the spawn-time worktree check. To test that check, kill the thread's process first: `kill $(ps -eo pid,command | grep fake-claude | grep <thread-id> | grep -v grep | awk '{print $1}')`.
- A fresh QA stack opens on the onboarding dialog, which swallows every click a browser script makes. Mark it onboarded first: `echo '{"onboardedAt":"2026-01-01T00:00:00.000Z"}' > "$QA_DIR/data/omni.config.json"`. On a `qa-handoff-stack.sh` server that file already holds sync settings, so set the one key instead of overwriting it: `node -e 'const f=process.argv[1],fs=require("fs"),j=JSON.parse(fs.readFileSync(f));j.onboardedAt="2026-01-01T00:00:00.000Z";fs.writeFileSync(f,JSON.stringify(j,null,2))' <dir>/a/data/omni.config.json`. A desktop QA `--out` inside the rig's dir goes with `down`.
- Playwright from `node_modules` can want a browser build that is not downloaded. Pass `executablePath` to a build already in `~/Library/Caches/ms-playwright/` (macOS) or `~/.cache/ms-playwright/` (Linux) rather than downloading one.
- A fresh worktree has no `node_modules`, so `@omni/server` types resolve to the main checkout's copy and typecheck misses (or invents) errors in your change. Tests do the same: `@omni/test-fixtures` resolves to main's fake CLIs, so a new fixture directive silently does nothing, and a wire fixture record run (`OMNI_RECORD_WIRE_FIXTURES=1`) rewrites the main checkout's `packages/test-fixtures/wire`. Run `npm ci --include=dev` in the worktree first (agent shells set `NODE_ENV=production`).
- npm can skip install scripts ("npm warn install-scripts ... Run `npm install-scripts ls`"), which leaves Electron without its binary, and `@omni/desktop#test` then fails with "Electron failed to install correctly". Run `rm -rf node_modules/electron/dist && node node_modules/electron/install.js` in the worktree.
- A `TMPDIR` outside `/tmp` (for example under `~/.cache`, to dodge a tmpfs quota) fails seven `@omni/server` files: `bundle-boot`, `wire-fixtures`, `stream-catch-up` and the `*-two-macs` tests. Run `npm test` with the default `TMPDIR`; keep the override for QA stacks only.
- `qa-stack.sh`'s `security` wrapper passes every call but the Cursor key to the real login Keychain, so saving a secret on a QA stack (Secrets, or a webhook's Set secret) writes it to Ben's Keychain. After `up`, overwrite `$QA_DIR/bin/security` with a stub (`-i` reads stdin and exits 0; `find-generic-password` prints a fixed value for the names you test) before saving any.
- On omarchy (2026-11-19) the harness's dev build can time out on `electron.launch` (60 s, stuck connecting to DevTools) even with `ELECTRON_OZONE_PLATFORM_HINT=x11`. `--app ~/Applications/Omni.AppImage` with `--app-url` on your 127.0.0.1 Vite launches at once and shows your Web UI change; it gets its own user-data folder, so the running installed app is untouched.
- The desktop QA harness only attaches. "no QA server on port N that owns <dir>" means the stack is not up or `dataDir` is not its `$QA_DIR/data`. It never starts a server itself, since one started from the checkout would run the real harness CLIs.
- Desktop QA on a tiling window manager (Hyprland, Omarchy): the manager sizes the app's windows, so a `size` step or the script's `size` may not hold once a second window opens. `qa.json`'s `facts.windows[].bounds` shows what the window got. On Ben's 4K screen the window can take all 3840x2160 at zoom 1, which makes the capture unreadable: pass `--zoom 2`, and reach content below the fold with `{"click": "text=<a heading>"}` then `{"press": "PageDown"}` before the screenshot. The manager can also give the window just the script's `size`: at zoom 2 a 1320px window is 660 CSS px, so the app shows the phone layout and desktop selectors time out. Check `facts.windows[].bounds` and rerun at `--zoom 1` when the width is under about 2000.
- A free port is not a free stack: two threads can run `up` on the same port in the same second, and the loser overwrites the winner's pid files in `$TMPDIR/omni-qa-<port>`. Pick a port whose `$TMPDIR/omni-qa-<port>` does not exist yet, and after `up` check each pid file's `/proc/<pid>/cwd` is your worktree.
- The desktop QA harness answers the system folder dialog itself (`folderDialog` step). To screenshot the real dialog on Omarchy without touching Ben's screen, add a Hyprland headless output (`hyprctl output create headless`, then `hyprctl eval 'hl.monitor({ output = "HEADLESS-N", mode = "2400x1500", position = "auto", scale = 1 })'`), move the app's and `xdg-desktop-portal-gtk`'s new windows to a workspace there with `hyprctl dispatch 'hl.dsp.window.move({ workspace = "name:qa", follow = false, window = "address:0x..." })'` (Hyprland 0.56 takes Lua dispatchers only), focus that workspace and hand focus back, `grim -g` the windows' box (the output also shows the bar and notifications), then `hyprctl output remove`.
- In the desktop QA harness, `text=Approve` is a case-insensitive substring match, so it can click a subtitle that says "approved" and still pass the step. Click buttons with `<scope> button:has-text("Approve")` and check the side effect through the API.
- In the desktop QA harness, a `{"click": "text=Skip setup"}` on a fresh stack's onboarding leaves the window on the Conductor's welcome thread. Route back with `{"route": "#/"}`.
- The `omni-browser` page draws overlay scrollbars (`offsetWidth === clientWidth` on a scroller), so its screenshots never show a scrollbar change. Read `getComputedStyle(el).scrollbarColor` there and screenshot the bar in the desktop QA harness, which draws classic ones. `emulateMedia({ forcedColors: "active" })` and `{ contrast: "more" }` do render, so forced colors and Increase contrast can be shot in the browser.
- A hidden page is hard to get: switching `omni-browser` tabs leaves the first one `visible`, and Hyprland ignores the desktop app's Window > Minimize. Fake it in the page through `browser_run_code_unsafe`: `Object.defineProperty(document, 'visibilityState', { configurable: true, get: () => window.__vis })`, set `window.__vis`, then `document.dispatchEvent(new Event('visibilitychange'))`. Count requests with `page.on('request')` in the same call (state does not persist between calls), and match `/api/k/<key>/...` too: a paired browser sends every API call on the keyed cookie path. `initialPriority` from a CDP `Network.requestWillBeSent` shows a fetch's priority.
- The thread's Browser panel says "The live browser is off" on a default QA stack. Start it with `QA_BROWSER=1 scripts/qa-stack.sh up` (it launches a real Chrome for the channel).
- The worktree branch can start on top of commits that are not on `main` (another local branch's work). Check `git log --oneline main..HEAD` before you start; if it lists commits you did not make, they end up in your PR. With your edits still uncommitted and not in those commits' files, `git reset --keep main` drops them from your branch only (the other branch keeps them).
- On Linux with Node 26, `apps/web/tests/live-history-measure.test.ts` fails to load ("No such built-in module: node:") on `main` too, and turbo then stops the other packages' tests. Run `npx turbo run test --concurrency=2 --continue` to get every package's result.
- npm prints anything shaped like a UUID as `***`, and an Omni worktree's path holds one. `npm prefix -w` then answers `.../worktrees/***`, and electron-builder (`scripts/dist.ts`, so any packaged desktop build) fails with `spawn npm ENOENT`. Package from an APFS clone at a path without a UUID: `cp -Rc <worktree> "$TMPDIR/omni-build"` (instant, no extra space), then build there. Never run git in the clone: its `.git` file points at this worktree.
- An agent shell inside Omni carries the live install's `OMNI_*` variables and the channel's `APNS_*` secrets, which fail `sandbox.test.ts` (4) and `push-config.test.ts` (1). Run the suite without them: `env $(env | grep -oE '^(OMNI_|APNS_)[A-Z_]*' | sed 's/^/-u /') npx turbo run test`.
- On Ben's Linux box (Omarchy, Node 26) 11 server tests fail on `main` too, with or without the Omni `OMNI_*` variables: `bundle-boot` (adopted checkout `.env`), the `*-two-macs` handoff, takeover, sync and switch suites, `stream-catch-up` (large retained history) and `wire-fixtures` `requests-*.json` (`event_id` null or number). Compare against that list before treating a server failure as yours.
- `scripts/qa-handoff-stack.sh up` can stop at "the servers did not link in 40s" with each side's changes held "waiting for Trust" (Linux, 2026-11-14). Run it with `QA_HANDOFF_KEEP=1`, then on each server `POST /api/sync/devices/<the other's machine id>/confirm-key` (ids from `/api/sync/status`, tokens in `<dir>/a|b/data/api-token`) and `POST /api/sync/now` on both twice. `/api/devices` then lists the other machine.
- On the `qa-handoff-stack.sh` rig, a worktree thread made on one server is refused on the other (`GET /api/sync/refused`: "cwd outside the home folder and the channel checkouts"), and channels made on A may not reach B. `PUT /api/sync/path-map` on each with `{"map": {"<other>/data": "<this>/data"}}`, create the repo channel on both, then edit the thread (a title `PATCH`) so it syncs again (2026-11-15).
- The QA stack's server runs `tsx` without watch, so a server change needs a restart (Vite hot-reloads only the Web UI). Restart just the server by its PID with the env from `/proc/<tsx pid>/environ`, and keep the stack's data. Then reload the page with `location.reload()`: a `browser_navigate` to the same URL with only a new hash keeps the page and its old data.
- After `down` and `up`, the browser still holds the old stack's pairing cookie and can show the pairing screen even on the `?pair=` link. Paste the new token from `status` into the field.
- iOS simulator: pass `--companion-path /opt/homebrew/bin/idb_companion` to `~/omni-tools/idb-venv/bin/idb` before the subcommand (`idb --companion-path ... ui tap --udid <udid> <x> <y>`, in points); after it, idb rejects the flag. Its default `/usr/local/bin/idb_companion` is absent.
- Inside an Omni thread, `apps/server/tests/push-config.test.ts` and `sandbox.test.ts` (`buildMcpConfig`) fail because the agent shell carries APNs and Omni MCP env vars. They pass under `env -i HOME=$HOME PATH=$PATH npx vitest run tests/<file>.test.ts`; rerun them that way before treating a failure as yours.
- On Linux, `apps/server/tests/automations-delete.test.ts` can end the server run with an unhandled `write EPIPE` from `secret-store.ts` (the libsecret child closes its stdin early). Every test passes; it shows on about one run in three alone. Rerun the file before treating it as yours.
- `apps/server/tests/review-notes.test.ts` ("sends every open note as one message") can fail about one run in three with the two note ids swapped: notes made in the same millisecond sort by random id (`ORDER BY created_at, id`). Rerun the file before treating it as yours.
- `apps/server/tests/cursor-runner.test.ts` ("delivers a held message and an interrupt sent after it, both, in order (F22)") can fail in a full `turbo run test` on Linux and pass alone (2026-11-18). Rerun the file before treating it as yours.
- `apps/server/tests/thread-tree-data.test.ts` ("a failed thread under a job > waits on the job that delegated it") fails about one run in three, on `main` too (2026-11-19, 2 of 6 alone). Rerun the file before treating it as yours.
- `apps/server/tests/hermes-runner.test.ts` can fail its teardown with `ENOTEMPTY ... omni-runner-*` (a late title call still writing `fake-claude.jsonl`), on `main` too. All its tests pass; rerun it alone. Metro with `CI=1` does not watch edits; restart your Metro process with `--clear` after syncing changed files before trusting screenshots.
- Vitest 5 can race while clearing the workspace's `.vitest-cache` after dependency installation. If parallel packages fail with `ENOTEMPTY`, rerun the affected packages with `turbo run test --concurrency=1`.
- iOS 27 simulator: `xcrun simctl openurl` to the dev client asks "Open in Omni OS?" first; `xcrun simctl launch <udid> app.omni-os.ios --initialUrl http://127.0.0.1:<metro port>` skips it. SecureStore can hang when the app launches right after the simulator boots; relaunch the app. The app pairs only over https: put a local https proxy in front of the QA server and add its root cert with `xcrun simctl keychain <udid> add-root-cert`, then pair with a code from `POST /api/auth/app-pairings`. A dev client older than a new native dependency fails to load the bundle; rebuild it with `npx expo run:ios`.
- On the MacBook Air (2026-11-12), the Nov 9 dev client in DerivedData loaded the bundle through `--initialUrl` with `EXPO_PUBLIC_OMNI_DEV_URL`/`_TOKEN` set to an http QA stack, and the JS ran ("Running main"), but the screen stayed white through relaunches and a simulator reboot. Unresolved: try the https proxy and a real pairing code, or rebuild the dev client.
- On the MacBook Pro (2026-11-17) the same Nov 9 dev client (`~/Library/Developer/Xcode/DerivedData/Omni-*/Build/Products/Debug-iphonesimulator/Omni.app`) ran fine on an iPhone 17 simulator against an http QA stack: `simctl install`, then `xcrun simctl openurl booted "exp+omni-os-ios://expo-development-client/?url=http%3A%2F%2F127.0.0.1%3A<metro port>"`, with Metro started from `apps/ios` as `CI=1 EXPO_PUBLIC_OMNI_DEV_URL=... EXPO_PUBLIC_OMNI_DEV_TOKEN=... npx expo start --dev-client --port <port> --localhost --clear`. Its `console.log` lines land in Metro's output, which is the easiest way to read timings from the app.
- On the remote iOS 27 simulator, `idb ui tap` can fail with an invalidated `dtuhidd` connection even after a simulator reboot. For a development-only fallback, drive navigation and existing press callbacks through Metro's Hermes inspector. Its WebSocket requires a matching `Origin` header (for example `http://127.0.0.1:<metro port>`). Keep any instrumentation outside the shipped source and report callback checks separately from physical tap checks.

- An `npm install --ignore-scripts` in a fresh worktree leaves node-pty unbuilt, and the server's `terminal`, `continue`, `message-context-terminal-runner` and `worktree-cleanup` tests then fail (timeouts, "reading 'screen'"). `npm rebuild node-pty` fixes them.
- In the desktop QA harness, a `route` step to `#/t/<id>/details` fails after 10 s because the page rewrites the hash to `#/t/<id>`, though the thread and its Details open. Follow it with an `expect` step and judge by that.
- Agent shells can inherit the live `OMNI_DATA_DIR` and APNs settings. `sandbox` then reads the real configured user instead of "the user", and `push-config` sees preconfigured keys. For test subprocesses, use a fresh temporary `OMNI_DATA_DIR`, remove `OMNI_CONFIG` and `APNS_*`, and leave the parent environment unchanged. Do not print their values.
- `env -i PATH="$PATH" HOME="$HOME" npm test` on Linux fails six `worktree-cleanup` tests with `spawn /bin/zsh ENOENT`: channel actions run in `$SHELL` and fall back to zsh. Pass `SHELL="$SHELL"` too.
- The Rust crates (`crates/`) have their own tests outside `npm test`. After a change there, run `npm run test:rust` with the Omni variables unset (docs/internals/rust-port.md). The server's tests build `omni-mcp` with `cargo` first. When `cargo --version` does not run they skip the ones that start it, so `[tests] no omni-mcp build` at the top of a server run means those went untested: put `~/.cargo/bin` on PATH (a mise shim with no Rust version counts as no cargo). A build that fails fails the run (`omni-mcp did not build`).
- `omni new` against a QA stack from inside an Omni thread fails with `FOREIGN KEY constraint failed`: it sends your live thread (`OMNI_THREAD_ID`) as the parent, which the stack does not have. Run it as `env -u OMNI_THREAD_ID OMNI_URL=<stack> OMNI_TOKEN=<stack token> omni new ...`.
- A hand run of `omni` (`scripts/omni.sh` or `target/debug/omni`) with the Omni variables unset looks for the install on :4747, the live server. Pass `OMNI_URL` and `OMNI_TOKEN` of a QA stack, or `OMNI_INSTALL_PORT=<a closed port>`, and close stdin (`</dev/null`): `omni new` without a prompt reads it.
