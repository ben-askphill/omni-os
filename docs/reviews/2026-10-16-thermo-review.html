Omni OS: thermo code-quality review

Review dated 16 October 2026 · audit baseline main @ d4045555944e1b107d53e8f833d202857635a450 · committed with the fix PR for findings 1 and 2

This is the durable record of a targeted code-quality audit of the runner, harness adapter boundary, sync file transfer and thread rendering paths. It keeps the original evidence and labels each finding by what kind of claim it is:

  • Confirmed bug reproduced deterministically against temp data dirs and the in-memory relay.
  • Traced risk supported by reading the code, not reproduced end to end.
  • Architecture debt a structural problem, not a claim that anything fails today.

Scope and evidence

  • Reviewed: runner lifecycle modules, the harness session contract and Codex input conversion, sync worker/apply/thread ownership/file transfer, the thread API, the Web composer and thread session state, and Markdown rendering in both clients.
  • Not reviewed: every harness internal, browser control, every Swift view, full history.
  • Baseline checks at the audit: npm test 111 files passed, 2 skipped; 1,045 tests passed, 7 skipped. npm run typecheck passed.
  • Two deterministic reproductions ran against temporary data and home dirs with MemoryTransport. No live database, Keychain, harness session or server was used.
  • Mac tests and browser rendering checks were not run at audit time. The renderer overlap in finding 5 was not reproduced.

Findings

P1 · Confirmed bug1. A timed-out session download can overwrite a newly running session · #192

Evidence (baseline). server/sync/files.ts:313-331: pullSession checks the local session is unchanged, awaits getObject at line 326, then replaces the file at line 331 without checking again. beforeResume (452-462) stops waiting after 15 s but does not cancel or fence the download, running or still queued behind serial(). spawnLive then starts the harness.

Failure. A slow download passes the unchanged check; the timeout lets the harness resume and append a turn; the download lands and replaces that file with the remote copy. Per-thread serialization orders sync jobs only; it does not lock out the harness writing the same file.

Reproduction. Temp home and data dirs, MemoryTransport. pushSession an initial file (previous turn), change the relay manifest and session body to remote turn, override relay.getObject for the session object so it writes new local turn while download pending locally before returning the remote body, then await pullSession:

{"reproduction":"local session changes while download pending","localEditPreserved":false,"finalBody":"remote turn"}

Fixed in this PR (bounded).

  • beforeResume returns an explicit outcome: ready, failed, timed-out or skipped. Whatever the outcome, it closes an AbortController fence when it returns: ownership passes to the harness at that point.
  • A job still queued behind another job of the thread checks the fence before it starts and never touches the relay.
  • pullSession records each file's size:mtime fingerprint before its download, fetches the whole set, then in one synchronous step with no await re-checks the fence and every fingerprint and either renames all files into place or none. A Cursor store.db and its -wal can no longer land from two different Macs on a timeout.
  • pullThreadFiles re-checks the fence and that the file is still absent right before its rename.
  • A kept local file is not recorded as synced, so the next pull keeps it too and the next push uploads it.

Traced risk, not fixed here. endTurn marks the thread finished before turnFinished uploads its files in a delayed background job, so another Mac can see a finished row while only an older session manifest exists. Cross-Mac continuation needs an explicit session revision/readiness marker published after the upload, required before resuming. Not reproduced with two Macs. Tracked separately in #194.

P1 · Confirmed bug2. File sync hashes one version and uploads another · #193

Evidence (baseline). server/sync/files.ts:155-164: pushThreadFiles hashes the file (155), awaits hasObject (157), reads the file again for putObject (158), then remember records the post-await size and mtime against the earlier hash (164). pushSession has the same shape.

Failure. A file that changes during the await is stored under the wrong content address. The receiver's hash check rejects it, and the local cache keeps the false hash against the edited file's size and mtime, so a normal retry does not repair it.

Reproduction. Temp OMNI_DATA_DIR set before the dynamic imports; artifacts/report.html = version-one; MemoryTransport.hasObject overridden to rewrite the file to version-two-with-edit and return false; pushThreadFiles:

{"reproduction":"file changes during hasObject","manifestHashMatchesStoredBlob":false,"storedBody":"version-two-with-edit"}

Fixed in this PR. One immutable snapshot per upload: bytes, their sha, size and the mtime from just before the read. Those exact bytes are uploaded, the manifest lists that snapshot, and the file is only recorded as synced if its current size and mtime still match the snapshot. An edited file stays dirty and goes up on the next pass. pushSession uses the same snapshot.

P2 · Architecture debt3. The runner was split into files without splitting ownership · #195

Evidence. Live holds process startup, turn state, CLI turn state, replay tracking, queue state, interrupt acknowledgement, shutdown, browser ownership, tasks, mods and exit bookkeeping, and several modules mutate it directly. server/runner/state.ts:163 adds mutable callback slots and bindPump, bindReportToParent, bindEndTasks to work around module cycles; runner.ts imports modules for their registration side effects. The eight runner modules total 1,631 lines.

Why it matters. Lifecycle invariants live in the order of mutations across queue, records, session and spawn. Startup, active and closing states are combinations of nullable fields and booleans rather than a small set of valid states.

Remedy. One composition root owns the live-session registry and builds a per-thread controller. Keep process lifecycle and turn lifecycle as separate explicit models (a warm process can outlive a turn). Route start, replay, result, interrupt and exit through the owner, inject scheduler and reporting effects at construction, delete the bind registry. No generic event framework. Not a claim that the current import order fails. Not implemented here.

P2 · Architecture debt4. The adapter boundary is Claude-shaped and untyped · #196

Evidence. server/harness/adapter.ts:64: HarnessSession.write(obj: unknown) is documented as receiving Claude-shaped messages. messageBody/userLine build Claude text/image blocks, read attachments synchronously as base64, and carry the original message again in _omni. codex/adapter.ts:75 omniOf accepts any and casts the side channel back.

Remedy. A typed send(message) and interrupt(requestId), or a small discriminated command union. Encoding, image reads and wire envelopes move into each adapter. Delete _omni and omniOf. Not implemented here.

P2 · Architecture debt5. A local prompt edit turns a renderer limitation into a global content contract · #197

Where it actually is. This edit is not on main and not on origin. At the time of this PR it is an uncommitted change to server/runner/prompts.ts in the canonical local checkout (/Users/benrosenberg/omni-os), so the locally running server already sends it to every agent. It is not part of this PR.

  • Around line 52 it replaces "Prefer a self-contained .html file for anything visual" with: write guides, reports and any document with headings, tables or code blocks as self-contained HTML, "never as Markdown: Omni's Markdown renderer has layout bugs".
  • Around line 73 it adds: keep every table cell under about 40 characters and never put a sentence in a cell, because "Omni does not wrap long cells, so they overlap the next row".

Problem. Every harness and both clients inherit a content restriction to work around a layout defect. A character count is unrelated to rendered width, and it cannot fix historic replies or content from other sources. The Web renderer has its own table overflow styles; the Mac app has a separate table view (mac/Omni/MarkdownView.swift). Neither overlap was reproduced, so this is an ownership finding, not a diagnosis of which view is broken.

Remedy. Keep HTML as an artifact preference if wanted. Reproduce and fix wrapping in the affected renderer with a long-cell fixture shared by both clients, then remove the 40-character rule. Treat the prompt text as a temporary workaround with a removal issue. Not implemented here.

Regression tests added

All drive the interleaving from inside the relay call, so they are deterministic. Each fails on the baseline files.ts, and each guard in the fix was removed in turn to confirm a test fails without it.

  • tests/sync-files.test.ts: keeps a session the harness wrote while the newer one downloaded, and keeps it on the next pull; writes none of a Cursor chat when one file changed during the download; keeps a thread file made here during its download; stores an artifact edited during upload under the hash of the bytes sent, the other Mac accepts it, and the edit goes up on the retry; same for a session file.
  • tests/sync-files-hooks.test.ts (real runner, fake CLI): a download that times out mid-transfer writes nothing; a download queued behind another job of the thread when it times out never starts (never reads the manifest); a failing download reports failed and the next resume reports ready.

Known residual limits of the fix

  • There is still a sub-millisecond window between the final fingerprint check and rename in which another process can write. Closing it needs a cross-process file lock with the harness, which the CLIs do not offer.
  • The per-file "changed here since the last sync, keep it" rule that predates this fix can still keep one file of a multi-file Cursor chat while taking another. The new all-or-none step only covers changes during the download.
  • After a timeout the resume job keeps the thread's job queue until its relay call settles; transports have no per-call timeout.
  • When the resume times out, the harness runs on this Mac's older session and the next upload replaces the other Mac's newer one on the relay (last writer wins). Losing remote turns is preferable to clobbering a local turn on disk, but it is a real tradeoff, and the readiness protocol (1b) is the real fix.
