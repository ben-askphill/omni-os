# Threads are group chats: agents seated as members

> Decided with Ben on 2026-11-20. Not built yet: [the group threads plan](../plans/2026-11-20-group-threads.md) splits the build into slices and lists what is still open. Until a slice ships, the user docs it names describe what runs.
>
> Parts superseded by [ADR 0021](0021-crew-avatars.md), decided 2026-11-21 and not built yet: an agent without a photo or an icon shows its crew character, not the initials disc, the built-in marks retire, and a character draws no ring and shows its state in its eyes, with the Needs you diamond beside the avatar instead of on it. Each line it replaces says so below. The rest of this ADR stands.

A thread today is one agent with one harness session. The glossary defined it as "one task's conversation with one agent", and [Ask an agent](../user/threads.md#ask-an-agent) says "Omni never seats a second agent in a thread". Ben has two ways to bring in another agent, and both make another thread. An Ask (`@agent` at the start of a message, or **Ask an agent…** in the thread's menu) starts a thread on that agent under this one. By default it carries an excerpt of up to 6,000 characters, and its answer comes back as a report card. A team (`delegate_team`) is a lead thread plus one member thread per part, drawn as a tree under the Conductor. Ben wants a thread to work as a group chat: several agents in one conversation, each answering when named, working on the same files.

## Decision

- **Every agent has a name and an avatar.** There is no per-agent voice. Ben uploads the avatar in Settings > Agents, or keeps an icon or emoji on a color as today, and it syncs to every machine with the agent's crew file, the phone included. Without any, the agent shows a colored disc with its initials. Built-in agents keep their marks. _(Superseded by [ADR 0021](0021-crew-avatars.md), D1 and D9: without either, the agent shows its crew character, and the built-in marks retire.)_ Agent names are unique, ignoring case, checked when an agent is saved. A remote agent can offer its own avatar when it connects ([ADR 0020](0020-remote-agents-are-agents.md)). Every message in a transcript shows the name and avatar of the agent that wrote it. The harness and model show beside them only with **Show technical details** on.
- **The lead.** The agent a thread started as is its lead, fixed once the thread starts. To change the lead, Ben starts a new thread. If the lead agent is hidden or deleted, the thread goes read-only, and Ben starts a new thread to carry on. A message that names no agent goes to the lead.
- **Seating.** An agent mention (`@agent`) in Ben's message seats that agent in the thread as a **member**, for good, with a session of its own in that thread. So does **Add an agent** in the member list, which seats it with a joined line and no turn. Ben seats agents the same way in any thread, #conductor threads and quick asks included; a member in a quick ask gets the quick ask's read-only tools. Any agent except the Conductor can be seated. If this machine cannot run it, its turn fails when it runs. A member stays until Ben removes it from the thread's member list. Removing it closes its session and keeps its past replies in the transcript. A member removed mid-turn finishes that turn, its queued messages are dropped, and the "left" line comes after its reply.
- **A member's run.** A member runs on its agent's run defaults, then the channel's, then Auto. Ben can switch one member's run from the member list.
- **Once per thread.** An agent is seated in a thread at most once. Naming a member again makes it reply. It never seats a second copy.
- **Routing.** A message that names one or more agents goes to each of them, and they reply in parallel. The lead stays quiet unless the message names it too.
- **What a member reads.** On its first turn, a newly seated member gets a **catch-up**: a summary of the thread so far, which Omni writes with a small model. The lead does not write it. After that, on each turn, an agent gets every message posted since its own last turn as context: Ben's, the lead's and the other members'. It never gets their tool calls or tool output. A remote agent in a channel that keeps its work from remote agents gets neither, only the message addressed to it ([ADR 0020](0020-remote-agents-are-agents.md)).
- **One worktree, parallel turns, own powers.** Every agent in a thread works in the thread's one worktree and branch. Their turns run at the same time, and each agent keeps its own powers and run. When two agents touch the same file, Omni tells each running agent which files the other changed this turn. The thread flags every file both of them edited (a **collision**). Changes shows one combined diff with no credit per agent: the collision flags are enough. A flag clears at the lead's next commit, or sooner when Ben dismisses it. Turn checkpoints are one per message across all agents, and undo restores the worktree as it was before that message.
- **Only the lead commits.** The lead is the one agent that commits and opens the pull request. Members edit files only. A remote lead never changes files ([ADR 0020](0020-remote-agents-are-agents.md)), so in a remote-led thread Omni shows Ben a **Commit** button for what local members edited, and Ben commits.
- **Cursor Cloud as a member.** A Cursor Cloud agent can be a member. It works on its own branch, and its changes come back as a separate diff. When it finishes, the lead pulls its branch into the thread's branch and resolves any conflicts.
- **Stop stops everyone.** Stop stops every running agent in the thread. There is no Stop for one agent. A message steers the agents it goes to under the routing rule: the ones it names, else the lead.
- **Moving a thread waits for everyone.** Handoff, Take over, fork and continue are refused until every agent in the thread is idle. Then every agent's session moves together.
- **Agents do not seat agents.** An `@name` in an agent's reply is plain text. It seats no one and wakes no one. The Conductor is the one exception for seating. It seats agents in its own #conductor thread (`seat_agents`) and in a delegated thread it creates in the client channel: when it creates the thread, and with agent mentions in its follow-up messages there. It never seats agents in any other #conductor thread. An agent it seats in its own thread talks with Ben there, opens its own thread in the client channel when the work needs files, a repo, a browser or a long run, and relays that thread's report (amended 2026-11-21, see below). A team lead is the one exception for waking: it messages its seated members their parts through a tool only a team lead gets, in its team thread, and that tool seats no one.
- **A team is one thread.** `delegate_team` makes a single thread in the client channel, with a lead and the members seated. The Conductor's brief goes to the lead, which runs a planning turn first, then messages each member its part. The members run in parallel. An agent with two parts gets one seat, and the lead gives it both parts in one message. Once every member has finished, Omni wakes the lead with their replies, and the lead writes the crew report. The lead waits while a member waits on Ben. A failed or stopped member counts as finished. There is no time limit. Ordinary delegation keeps its shape: `delegate` still makes a thread of its own with a task id and a crew report, and now takes an optional member list.
- **When the crew report goes.** A delegated thread's crew report goes when the lead's turn ends, even if members are still running. In a team thread, that is the lead's turn after every member has finished, not its planning turn.
- **The status mark shows the busiest agent.** A thread's mark is the highest state among its agents, in this order: Needs you, then Failed (with Usage limit, Setup failed and Message held), then Working, then Done (with Stopped), then Idle. Avatars on the mark show which agents are running and which one waits on Ben, wherever the mark shows (see How it looks).
- **Seating replaces Ask for new messages.** An agent mention no longer starts a thread under this one with a report card. Asks already sent stay readable as they are.

## How it looks

Ben picked these on 2026-11-20 from a throwaway prototype that draws each screen on desktop and phone (branch `prototype/group-threads`, never merged). The variants he turned down stay behind its switcher.

- **Who wrote a reply.** An agent's avatar sits in a gutter left of its reply, at 24px, with its name and the time on the line beside it. Replies in a row from one agent share one head. Ben's messages stay right-hand bubbles.
- **Default avatars.** The initials disc shows two letters, unique across agents: Researcher is RS and Reviewer is RV, never both RE. Below 18px the disc shows its color only. _(Superseded by [ADR 0021](0021-crew-avatars.md), D1: the initials disc is retired. An agent without a photo or an icon shows its crew character, drawn for each size from 16px.)_
- **Joining and leaving.** When an agent is seated, a quiet line in the transcript says so ("Designer joined"). Removing a member writes the same kind of line ("Designer left").
- **Agent mentions.** The composer keeps one `@` menu, with tabs: **Machines | Agents | Files**. It opens on Agents, which lists the thread's members, then the agents a mention would seat. Artifacts sit in the Files tab under a heading of their own. With no `@` in the message, the composer's placeholder names the lead ("Reply to Builder"). Once Ben types an `@`, a hint line under the composer says who gets the message ("Goes to Designer only"), and that a new agent joins the thread and stays until Ben removes it.
- **Mention pills.** An agent pill carries the agent's avatar, in the agent's own color: the main color of its image, else its initials disc's color. _(Since [ADR 0021](0021-crew-avatars.md), D4 and D13: else the agent's color, its `bg` or its shape's paired color.)_ A machine pill carries a device icon, in the current blue.
- **The model picker.** With several agents in the thread, the composer's model picker changes only the lead's model.
- **The member list.** The members' avatars sit at the right of the thread header. They open the member list, a popover on desktop and a sheet on the phone, with **Add an agent**, and with Remove and the member's run on each member. The quick-actions card keeps a Lead row and a Members row, with their avatars. The header's avatars are the only sign of who is working: a running agent's avatar gets a ring, and the header has no Working label. _(Ring superseded by [ADR 0021](0021-crew-avatars.md), D8: a crew character draws no ring and shows working in its eyes. Photo and icon avatars keep the ring.)_
- **Parallel turns.** While several agents answer one message, the turn splits into a lane per agent, each with its steps and the files it changed. The lanes stay as lanes in the history after the turn ends. With three or more agents running, the lanes stack vertically, each collapsed to its latest line. A collision flag sits above the lanes. It names the file with its folder (`thread/Composer.tsx`) and shows the full path on hover. The phone shows one lane at a time, with a tab per agent.
- **The status mark in a list.** On desktop, the agents' avatars are the mark while any of them runs or waits on Ben. The agent waiting on Ben comes first and on top, with the Needs you ring and the Needs you diamond on its corner. Agents that run follow in the Working ring. _(Superseded by [ADR 0021](0021-crew-avatars.md), D8: a crew character draws neither ring and shows its state in its eyes, and the Needs you diamond sits beside the avatar, not on its corner. Photo and icon avatars keep the rings.)_ The mark shows two avatars at most, else one and a count. Other states keep today's mark. When one agent has failed while another still works, the mark shows the working avatar, and the row adds a red dot for the failure: Failed outranks Working in the order only, not in the mark. On the phone, the row's second line says who asks and who works, with their avatars ("Builder asks you · Designer working"). Inbox cards, phone Activity and the Overview dashboard draw the same avatar mark, two at most, else one and a count.

## Considered

The reasons below follow from Ben's decisions. The session that settled them did not record a reason for each option it turned down.

- **Keep Ask, and show its answer inline.** The answer would still come from a session that saw only an excerpt, framed as data, and every follow-up would need another Ask. A seated member keeps its session and reads the thread as it grows.
- **A worktree per member.** Two agents could not build on each other's changes without merging branches, and one thread would carry several branches and pull requests. One worktree keeps one branch and one diff per thread. The cost is collisions, which the warnings and flags make visible.
- **Members taking turns.** Naming several agents is a request for several answers. Taking turns makes each one wait for the slowest.
- **Agents mentioning each other.** Two agents could wake each other back and forth with nobody reading, and the work would leave Ben's hands. The Conductor's exception is bounded the way delegation already is: threads it creates, in a client channel.
- **Members see tool calls.** Tool output is most of a turn's size, and it would fill every member's context. A member that needs the files reads the shared worktree.
- **Several copies of one agent.** `@builder` would no longer name one agent, and two sessions with one charter would split one role's work.
- **A lead that hears every message.** It would answer messages meant for members and spend a turn on each one.
- **The lead writing the catch-up.** Ben first chose it, then moved the catch-up to a small model that Omni runs. He gave no reason.
- **Changing the lead, a Stop per agent, members that commit, and credit per agent in Changes.** Ben turned these down when he answered the plan's questions. For credit per agent, he said one combined diff and the collision flags are enough. He gave no reason for the others.
- **Members starting on their parts at once, with the team lead waiting for them.** Ben chose a planning turn first. He gave no reason.
- **Other layouts.** For each screen in How it looks, the prototype drew two to four layouts: a byline or a card per reply, a To line of recipient chips above the composer, a members strip under the title, collisions inline in the transcript or in a dock over the composer, and the mark with avatars beside it. Ben did not record why he turned them down.

## Consequences

- A thread has one session per seated agent. Everything that assumes one session per thread moves to one per agent in the thread: resume, warm state, the context meter, limit stops, switching a run, handoff to another machine and fork.
- Transcript rows record the agent that wrote them, and the member list syncs to the other machines.
- Each member's spawn gets a thread token of its own ([ADR 0016](0016-thread-bound-credentials.md)). An agent's `access` still only narrows the channel's access level ([ADR 0015](0015-access-levels.md)).
- Cursor Cloud works on its own cloud checkout, so a Cursor Cloud member's changes stay off the thread's branch until the lead pulls them in.
- The commit flow gains a path where Ben commits: the Commit button in a remote-led thread.
- Seating a member costs a small-model call: Omni writes the catch-up before the member's first turn, as it already writes thread titles and follow-ups.
- A thread whose lead agent is gone stays readable but takes no new messages.
- A team lead gets one tool no other agent has: it messages its own team thread's members.
- Undo works per message, so it also undoes what every agent changed for that message.

## Amendment 2026-11-21: the Conductor seats first

Ben wanted a new Conductor thread to bring the right agent into the conversation, not to hand the work off at once. The Conductor now seats the agent in its own #conductor thread for any real work, with `seat_agents`. The seated agent answers there and decides when the work needs a thread of its own. It opens one with `omni new` in the client channel, as itself. That thread's parent is the agent's session, so its crew report lands in the #conductor thread as that agent's, and wakes the agent to relay it. The thread records that #conductor thread and the agent when it is made (`job_id` and `seat_agent`, filled in by a migration for threads from before), so the lists (the sidebar, the Inbox, phone and iOS Activity) nest it under the #conductor thread, not under the hidden session, as they nest a thread the Conductor delegated, and its delegation card shows there, without looking the seat up on each read. The Conductor still uses `delegate` directly for reviews, a team Ben asked for, and when Ben asks it to delegate. A task on a machine Ben mentioned is seated too, with that machine's id, so the thread the agent opens runs there. The server allows it only in the Conductor's own thread (a `delegate_only` agent leading a #conductor thread); every other #conductor thread still refuses an agent's seating.
