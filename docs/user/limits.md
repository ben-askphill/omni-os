# Known limits

- Tool failures reported by Claude Code, Codex, Cursor and Hermes are captured automatically on the Mac that runs the thread. Ask the Conductor to inspect tool failures and record remediation guidance, or turn on the `tool-failure-triage` automation for a daily review that opens fix PRs. The grouped log is also available at authenticated `GET /api/tool-failures`; it lives in `data/omni.db`, in `tool_failures` and `tool_failure_triage`. No new client screen is required, so desktop web, phone web and the desktop app use the same Conductor workflow. Shell failures are filed by exit code, not by words in the command output, and a Cursor call rejected before it starts keeps its tool name. Read, MCP and DesignSync misses land in `not_found`, `invalid_input` or `authentication` rather than `unknown` ([Architecture overview](../internals/overview.md)).
- Failure capture depends on harness failure signals. Hidden inner calls, tools returning a success flag with error text, unreported child calls, process crashes without a tool result and tools run outside Omni need an agent report or remain unobserved. A failed logger prints a fixed server-log message and does not stop result delivery. No historical transcript backfill runs. Logs and remediation stay local to this Mac and survive thread deletion; sync does not copy them.

- Isolation is a worktree plus a browser profile, not a VM. Threads run with `bypassPermissions` because nobody can answer prompts headless; the write boundaries in your workspace folder's CLAUDE.md still apply.
- Only one live thread per channel gets the persistent browser profile; parallel ones get an isolated browser. The channel's Chrome closes after 5 idle minutes.
- Worktrees are removed only by a cleanup (`apps/server/worktree-cleanup.ts`), never on their own unless this Mac's retention policy is on. Storage, under Settings > Worktrees, lists what a cleanup would remove: worktrees of archived or deleted threads, and of threads whose branch is merged into origin's default branch (HEAD in it, or a squash-merged PR into it whose head is HEAD and whose merge commit it has) and idle for 7 days (`OMNI_WORKTREE_IDLE_DAYS`). Ben reviews the list and removes it, or turns on retention for this Mac (off by default, saved in `data/omni.config.json`, never synced), which removes the ones idle for its number of days a minute after startup and then daily. Right before each removal the server checks the worktree again with its folder held, the way a turn, a terminal, a channel action or a checkout holds it: changes, untracked or ignored non-build files, unpushed commits, a running, queued or held turn, an open terminal, a running channel action, another thread in the folder or a check that fails all keep it. Untracked copies of harness config that origin's default branch tracks (`.codex/`, `.agents/`, `AGENTS.md`, copied into worktrees made before main had them) are not work: they keep nothing and are deleted just before the removal. Removal is `git worktree remove` without `--force`. The branch, the transcript, uploads and artifacts stay, the last commit is kept as `refs/omni/removed/<thread>`, and the next turn checks the branch out again (making it again from that commit if it was deleted).
- Storage (under Settings > Worktrees, and the Conductor's `worktree_storage`) lists every folder in `data/worktrees` with its size, owning thread and why it is kept or eligible for cleanup. The inventory scan is read-only and runs in the background, two folders at a time, and can be cancelled. A folder counts as managed only when a thread (or its `omni/<id>` branch, once the thread is deleted) ties it to a repo a channel uses; anything else is a leftover folder that is listed and kept. Besides the cleanup guards it also keeps a folder that another open thread shares, that holds ignored files other than build output (`.env`, local config; build output includes `node_modules`, `.build`, `.swiftpm`, `.expo`, `apps/ios/ios`, `apps/desktop/release`, and a `data/` folder holding only a test server's database and empty folders), or whose branch has an open pull request. Stale registrations (git lists the worktree, the folder is gone) are shown apart: `git worktree prune` drops them and frees nothing, and never removes an existing folder.
- Strip caches (Settings > Worktrees) deletes the build output and installs in idle worktrees and keeps the worktrees: the ignored entries the scan counts as build output (`node_modules`, `.build`, `dist`, `.turbo`, `.swiftpm`, `.expo`, `apps/ios/ios`, `apps/desktop/release`, a test server's leftover `data/` and the like), measured per worktree as `cacheBytes`. It lists thread worktrees, open threads too, whose thread has had no turn or message for its idle days (7 by default) and that nothing is using. Ben reviews the list and strips it, or turns on the daily schedule for this Mac (off by default, saved in `data/omni.config.json`, never synced), which runs right after the retention pass. Each worktree is checked again with its folder held, as for a cleanup: a running, queued or held turn, an open terminal, a running action or another thread in the folder skips it, and so does a turn since the scan. Changes, untracked files, commits, `.env` and every other ignored file stay; a link named `node_modules` is removed, never followed. The next build or `npm ci` makes the caches again.
- Free disk space is checked a few seconds after startup and every 10 minutes (`apps/server/disk-space.ts`): the disk with `data/` and, when it is another disk or a Linux `/tmp` tmpfs mounted with `usrquota`, the temp folder the agent CLIs write command output to. Node cannot read a tmpfs user quota, so that one is estimated: the limit is `usrquota_block_hardlimit` from the mount options, else 80% of the tmpfs (systemd's default), less what this user's own entries in it use (`du`). Below 20 GB free (or 15% of a small volume) the level is low, below 5 GB (or 5%) critical. A change of level is logged (`[disk]`), and while it is not ok the desktop sidebar (web and desktop app) and the phone's Activity screen show a notice that links to Settings > Worktrees. `GET /api/disk` and the Conductor's `disk_space` return the last check. Nothing is held or deleted: it only warns.
- Restarting the server ends running turns as failed. Messages that had not reached a harness yet are kept as `recovered` and wait for Resume; one that may have reached it is marked `uncertain` and goes again only when you say so.
- Subscription limits still apply. Each harness has its own concurrency cap (12 by default): `OMNI_MAX_CONCURRENT` (Claude Code), `OMNI_MAX_CONCURRENT_CODEX`, `OMNI_MAX_CONCURRENT_CURSOR`, `OMNI_MAX_CONCURRENT_HERMES`, `OMNI_MAX_CONCURRENT_CURSOR_CLOUD`. A full harness never holds up threads on another. Hermes also enforces its own concurrent-run cap; Omni backs off and retries on HTTP 429.
