# Known limits

- Tool failures reported by Claude Code, Codex, Cursor and Hermes are captured automatically on the Mac that runs the thread. Ask the Conductor to inspect tool failures and record remediation guidance. The grouped log is also available at authenticated `GET /api/tool-failures`; it lives in `data/omni.db`, in `tool_failures` and `tool_failure_triage`. No new client screen is required, so desktop web, phone web and Mac use the same Conductor workflow.
- Failure capture depends on harness failure signals. Hidden inner calls, tools returning a success flag with error text, unreported child calls, process crashes without a tool result and tools run outside Omni need an agent report or remain unobserved. A failed logger prints a fixed server-log message and does not stop result delivery. No historical transcript backfill runs. Logs and remediation stay local to this Mac and survive thread deletion; sync does not copy them.

- Isolation is a worktree plus a browser profile, not a VM. Threads run with `bypassPermissions` because nobody can answer prompts headless; the write boundaries in your workspace folder's CLAUDE.md still apply.
- Only one live thread per channel gets the persistent browser profile; parallel ones get an isolated browser. The channel's Chrome closes after 5 idle minutes.
- Worktrees are removed only by a cleanup (`apps/server/worktree-cleanup.ts`), never on their own unless this Mac's retention policy is on. Settings > Storage lists what a cleanup would remove: worktrees of archived or deleted threads, and of threads whose branch is merged into origin's default branch (HEAD in it, or a squash-merged PR into it whose head is HEAD and whose merge commit it has) and idle for 7 days (`OMNI_WORKTREE_IDLE_DAYS`). Ben reviews the list and removes it, or turns on retention for this Mac (off by default, saved in `data/omni.config.json`, never synced), which removes the ones idle for its number of days a minute after startup and then daily. Right before each removal the server checks the worktree again with its folder held, the way a turn, a terminal or a checkout holds it: changes, untracked or ignored non-build files, unpushed commits, a running, queued or held turn, an open terminal, another thread in the folder or a check that fails all keep it. Removal is `git worktree remove` without `--force`. The branch, the transcript, uploads and artifacts stay, the last commit is kept as `refs/omni/removed/<thread>`, and the next turn checks the branch out again (making it again from that commit if it was deleted).
- Storage (Settings > Storage, and the Conductor's `worktree_storage`) lists every folder in `data/worktrees` with its size, owning thread and why it is kept or eligible for cleanup. It is read-only: the scan runs in the background, two folders at a time, and can be cancelled. A folder counts as managed only when a thread (or its `omni/<id>` branch, once the thread is deleted) ties it to a repo a channel uses; anything else is a leftover folder that is listed and kept. Besides the sweep's guards it also keeps a folder that another open thread shares, that holds ignored files other than build output (`.env`, local config), or whose branch has an open pull request. Stale registrations (git lists the worktree, the folder is gone) are shown apart: `git worktree prune` drops them and frees nothing, and never removes an existing folder.
- Restarting the server ends running turns as failed. Messages that had not reached a harness yet are kept as `recovered` and wait for Resume; one that may have reached it is marked `uncertain` and goes again only when you say so.
- Subscription limits still apply. Each harness has its own concurrency cap (4 by default): `OMNI_MAX_CONCURRENT` (Claude Code), `OMNI_MAX_CONCURRENT_CODEX`, `OMNI_MAX_CONCURRENT_CURSOR`, `OMNI_MAX_CONCURRENT_HERMES`, `OMNI_MAX_CONCURRENT_CURSOR_CLOUD`. A full harness never holds up threads on another. Hermes also enforces its own concurrent-run cap; Omni backs off and retries on HTTP 429.
