# Crew and Conductor

Each role is a file in `crew/*.md` with frontmatter and a charter. Edit them freely; Omni reads them on every run.

| Role | For |
| --- | --- |
| conductor | Front agent in #conductor. Routes every task to a crew thread, never does the work |
| researcher | Research, audits, answers to client questions, HTML reports |
| store-ops | Shopify store work, PSI/SEO, translations, imports |
| builder | Code in a repo channel, own worktree, opens PRs. |
| reviewer | Reviews a PR against its brief, from the spec and diff only. Read only |
| inbox | Mail, calendar, Productive, Notion, Slack drafts. Never sends on its own |
| usage-scan | Leads Scan my usage in #inbox: turns the repeated asks Omni found into up to 3 suggested automations ([Automations](automations.md#scan-my-usage)). Omni starts it; not for delegation |

The frontmatter sets each role's model and, for conductor and inbox, its default channel. The conductor defaults to `model: auto`, so the Overview and Conductor composers start on Auto; a saved #conductor channel default still wins (see [Auto](harnesses.md#auto)). The other roles also default to `model: auto`, so each delegated brief gets the model it needs. Pin a model in a role's frontmatter to opt it out.

The conductor reviews every PR a builder reports on the other model family from the one that wrote it, read from the builder thread's harness and model (`get_thread`): Codex `gpt-6.1-sol` at `xhigh` for a PR Claude wrote, following `/code-review:code-review` from the `gpt-review` skill where the machine has it in `~/.agents/skills`, else the reviewer charter's own steps; Claude Code `claude-opus-5-5` at `xhigh` for any other. When that harness or model is unavailable, or the builder's model does not say its family, it asks you instead of reviewing on the same family.

`delegate_only: true` in a role's frontmatter makes it a router that runs without the tools that do work. The conductor sets it, and so does usage-scan, which only reads its first message and saves what you pick.

- Claude Code: `--disallowedTools` for Bash, Edit, Write, NotebookEdit, Agent, Task, Workflow, Artifact, ArtifactData and the browser MCPs.
- Codex: a `read-only` sandbox.
- Cursor Agent: its own config folder in the thread's data dir, passed as `CURSOR_CONFIG_DIR`. Its `cli-config.json` is a copy of yours with `Shell(*)` and `Write(**)` added to `permissions.deny`; everything else in the folder links to yours, so the login and chats stay put. Deny rules hold under `--force`, and MCP tools stay allowed. Cursor's read-only `--mode ask` is no use here: with `--force` it blocks nothing, and without it it blocks the `omni` tools too.
- Hermes and Cursor Cloud: refused. A thread there gets no `omni` tools, and Hermes takes no per-run tool limits, so a router could only do the work itself. Creating such a thread fails with the reason, and a Hermes thread that already has the role fails its turn the same way.

None of them gets the `omni-browser` MCP, and the system prompt drops the Artifacts and Browser sections for a "delegate first" rule. A router can still read files, search and use the `omni` tools to write a brief.

The conductor's `omni` MCP (`apps/mcp/omni.ts`) exposes `list_channels`, `list_crew`, `list_harnesses`, `harness_accounts`, `delegate`, `delegate_team`, `file_thread`, `message_thread`, `mark_thread_done`, `recover_thread_session`, `switch_thread_run`, `continue_thread`, `get_thread`, `list_threads`, `list_pull_requests`, `search_history`, `list_published_artifacts`, `check_artifact_comments`, `list_claude_artifacts`, `refresh_claude_artifacts`, `list_devices`, `machines`, `hand_off_thread`, `signed_in_devices`, `revoke_signed_in_device`, `rotate_install_token`, `mcp_clients`, `remove_mcp_client`, `send_to_grok_bot`, `read_referenced_thread`, `watch_pr`, `set_auto_merge`, `crew_prs`, `rerun_failed_checks`, `crew_questions`, `list_review_notes`, `list_automations`, `run_automation`, `set_automation_enabled`, `delete_automation`, `get_automation`, `save_automation`, `list_automation_deliveries`, `retry_delivery`, `skip_delivery`, `set_automations_machine`, `scan_usage`, `list_channel_actions`, `run_channel_action`, `worktree_storage`, `disk_space`, `settings`, `set_secret`, `sent_secrets`, `insights`, `tool_failures`, `triage_tool_failure`, `note_tool_failure_recovery`, `omni_connect_status`, `omni_connect_set`, `omni_update`. A tool that takes a `thread_id` also takes its first 8 characters or its `omni/<id>` branch, as the `omni` command does, looked up among the latest 500 threads. A delegated thread runs in the target channel; when it finishes, Omni posts its reply to the conductor as a crew report (tagged with the task id) and wakes the conductor to relay it. In the sidebar, the Inbox and phone Activity, each Conductor thread shows its delegated threads (and a team's members under their lead) as a tree under its row; how it opens, closes and what it lists are in [Threads](threads.md). The parent's header shows an overlapping avatar for each channel its delegated threads work in, once per channel and finished threads included, with every channel named in its tooltip. It shows only when one of them works outside the parent's own channel, draws four discs at most (three avatars and a +N chip past four channels), sits in the sub line on a phone and opens the parent's Details. The parent's Details tab lists its delegated threads, and the Conductor's channel page on the desktop still nests them under their parent. The phone Conductor list keeps a delegate count that opens the parent's Details. Any crew role whose frontmatter includes the `omni` MCP (Claude Code, Codex or Cursor Agent), except usage-scan, also gets a short Thread delegation section in its system prompt: use `delegate` or `delegate_team`, call `list_crew` and `list_channels` for valid ids, and write each brief as Goal, Done when and Proof back, since the child thread cannot see the parent's chat.

A parent follows up on a thread it already has with the prompt cache in mind (`apps/server/session-warmth.ts`). A thread's session counts as warm while it runs, before its first turn, and for an hour after its model's last reply, tool call or turn end; `get_thread` shows this as `session` (`warm`, `last_activity_at`, `idle_minutes`). A warm thread gets `message_thread`. The parent does not wake a cold one. It opens a new session with `continue_thread` or delegates a fresh thread that links it, and says which thread replaced which. `message_thread` (a send `from: "conductor"` to `POST /api/threads/:id/messages`) returns 409 for a cold thread unless it passes `wake_cold: true`, for when you asked to resume that thread itself. Your own messages from the composer are never refused. The hour is the best case. The provider can drop a cache sooner, for example to 5 minutes in overage, and Omni cannot see that.
