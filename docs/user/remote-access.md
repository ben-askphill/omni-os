# Remote access and security

## From your phone

Run the production server and put it on your tailnet:

```bash
npm run build && npm start
tailscale serve --bg 4747
```

Then pair the phone once. The quickest way is the QR code under [Pair a phone's browser](#pair-a-phones-browser). From a terminal, print a pairing link with the `.ts.net` address instead:

```bash
OMNI_URL=https://<your-mac>.<tailnet>.ts.net omni open --pair
```

Open that link on the phone (AirDrop it, or paste it). Or open the `.ts.net` address and paste the token from `data/api-token` into the pairing screen. Once a Google account is linked (below), the pairing screen also offers Sign in with Google, so a new device needs no token at all. The server itself listens only on loopback, and Tailscale forwards requests to it. The Mac has to be awake. The server keeps it from idle-sleeping while it runs, so leave the Omni app open.

Every client names the Mac its Omni runs on: the desktop sidebar's footer (in a browser and in the desktop app) and the phone's Channels and Settings headers. A browser on another device gets a Remote chip, and its tab title starts with that Mac's name.

On an iPhone, open the `.ts.net` address in Safari and use Share, then Add to Home Screen. Omni then opens full screen with the phone layout: Activity, Channels, Library and PRs tabs, and a + button for a new delegation. A home-screen app can keep its own cookies apart from Safari's, so if it opens on the pairing screen, pair it once more with a new code.

## Pair a phone's browser

A phone's browser needs no token. In Settings in the desktop app, open Sharing & access, choose Pair a phone, then Phone browser, pick the address the phone will use and make a code. Scan the QR code with the phone's camera: it opens Omni on that address already signed in, with its own revocable browser session that shows under Signed-in devices. The code expires after five minutes and works once; an expired or used one opens the pairing screen with a line saying so.

## Pair the native iOS app

In Settings, open Sharing & access, choose Pair a phone, then iPhone app. Pairing takes the install token: make the code in the desktop app, or in a browser you paired with the token (`omni open --pair` prints its link). A browser that signed in with Google or a pairing code sees where to go instead of a code.

Pick the address the phone will use. The card offers this page's address when it is HTTPS, then the Omni Connect address while the tunnel is connected. For Tailscale, run `tailscale serve --bg 4747`, open "Use another address" and enter your `.ts.net` name. The card cannot check that the phone reaches an address you typed.

Scan the QR code or type the manual code in the app. The code expires after five minutes and works once. The phone gets its own revocable app session, not the install token. Revoke a session under signed-in devices. A paired phone has the same access as a Google session: it can start agents, but not open the thread terminal, add, edit, run or retry a channel action, or write an automation's precheck. Revoking does not undo what its agents already ran.

Once paired, the native app's tabs are Activity (phone web's Inbox list), Channels and Library, with New at the end of the tab bar. Settings uses the same shared catalog as the Web UI, including Channel Settings and About (native build, runtime and running update). Channel rows and headers show emoji, icon and SVG avatars. A push alert shows the thread's title, what happened (Finished, Failed, Needs your answer, a pull request that needs attention, or a crew report) and a plain-text preview of the reply, question or report. If alerts never arrive, Notifications and the Pair a phone card name the missing APNs secrets (`APNS_AUTH_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID`). Saving those secrets loads them without a server restart. Details are in [apps/ios/README.md](../../apps/ios/README.md) and [Native app pairing](../internals/app-pairing.md#push-delivery).

## Without Tailscale

[Omni Connect](omni-connect.md) gives each machine a Cloudflare tunnel and a public `https://<name>-xxxxxx.omni-os.app` address, through your sync relay. Sign in with Google once on the relay's Connect page, then open any machine from there. Every request still needs the token or a session.

## The phone layout

Below 768px, the Web UI uses its phone layout, whether opened in a browser or saved to the home screen.

- Activity shows the desktop Inbox view's list: pinned threads, the threads waiting on you, and the Working and Done shelves (see [Threads](threads.md#finding-threads-and-clearing-needs-you)). Each card names the machine and, while a turn runs, how long it has gone. With sync on, a sideways strip of machine tiles sits above the list (running threads, harness slots, live CPU and RAM). Tap a row to open its thread. Its check marks it done, and the undo on a Done row puts it back.
- Channels groups clients, internal and personal channels. A channel shows collapsible folders and ungrouped threads in Active and Recent tabs, a page at a time: Show older threads loads more, here and on desktop web (the iOS app loads more as you scroll). Active means Needs you or running. Both tab counts include folded folders. You manage folder order and context menus on desktop.
- Library lists artifacts with thumbnails, and a Files / claude.ai switch lists your Artifacts on claude.ai the same way the Artifacts page does ([claude.ai Artifacts](claude-artifacts.md)). Open one full screen to read or share it.
- PRs lists the pull requests of every channel with a GitHub repo. Search matches title, number, author, branch and repo (and `label:` tokens). Sort and filters narrow the list, and rows group into Authored, Review requested and Others for your `gh` login. Tap one to open it on GitHub. Desktop web and the desktop app show the same list at `#/prs`. The page names any repo gh cannot read under the list, and the rest still show.
- The + button starts a thread with the Conductor or a channel, with model and effort choices, attachments and dictation.

A thread shows each prompt and answer before its folded steps. Tap the step count to open them. Thread options opens Details, PRs, Changes, Browser, Terminal or Actions full screen. Details has the branch card and agents. The PRs screen lists the branch's pull requests, Watch PR, checks (with Rerun failed checks when a GitHub Actions check failed), Auto-merge and a slide to squash and merge. Changes pins review notes on the diff and can send the open ones to this thread or a delegate. Browser is watch-only and supports annotations. Terminal is read-only with tap-to-select output for a message, and never starts a shell: with none running, it says to open the Terminal tab on the desktop. Automations, Secrets, Sync, Storage and settings pages without a phone-specific screen use the desktop page under a back bar.

Links and reloads return to the same screen. Back uses the parent screen when there is no in-app history. Home-screen setup does not add iOS Live Activities or a lock-screen view.

## Sign in with Google

Link the Google account that owns this Omni once, and new devices sign in with it instead of the token. Each one gets a session of its own that you can see and revoke. Sign-in goes through Clerk ([ADR 0007](../adr/0007-google-sign-in-through-clerk.md)). Anyone with a Google account can make a Clerk account, but only the one linked to this install gets in.

1. On a device that already holds the token (the desktop app, or a paired browser), open Settings, Sharing & access, Google account, and choose Link Google account.
2. Omni shows a code and opens Clerk's sign-in page. Sign in with Google there, check the page shows the same code, and approve.
3. On a new device, open Omni and choose Sign in with Google on the pairing screen. Approve the code the same way, with the same account.

- Settings lists signed-in devices under the account, with when each was last used. Revoke ends one. Sign out on the device you are using ends its own. A session unused for 90 days stops working.
- Only the install token or a session paired with it can link, change or unlink the account. Linking another account or unlinking signs out Google sessions. It does not affect native app pairing sessions or browsers paired with the token.
- Signing in needs Clerk and the network. A device that already signed in keeps working offline.
- Omni uses a shared Clerk instance by default. `integrations.clerkPublishableKey` and `integrations.clerkClientId` in `data/omni.config.json` (or `OMNI_CLERK_PUBLISHABLE_KEY` and `OMNI_CLERK_CLIENT_ID`) point it at your own. Its OAuth application must be public, with the device authorization grant turned on. Both values are public. Omni holds no Clerk secret key.
- The Conductor lists signed-in devices with `signed_in_devices` and revokes one with `revoke_signed_in_device`.

## Who can call the API

Every `/api` request needs this install's token, or the session of a device that signed in with Google (above). The server makes it on first start: 32 random bytes in `data/api-token`, mode 0600, so only your macOS account can read it (`OMNI_TOKEN` in the server's environment replaces it, for tests and throwaway servers). The token is a file rather than a Keychain item because the desktop app and shell scripts read it without a Keychain prompt, and the Keychain would guard it from the same account the file mode already lets in. To rotate it, press Rotate install token on the Install token card in Settings, Sharing & access, then Rotate and sign out all (or use the Conductor's `rotate_install_token`). It works with the install token itself, from this Mac's desktop app or from a browser paired with the token, and from a thread's own token unless an automation or a usage scan sits above that thread. A Google, Omni Connect or iOS app session gets a 403. Omni writes a new token to the file, ends every signed-in and paired device session, and the desktop app pairs its window again by itself. Only browsers, phones and the iOS app pair or sign in again by hand. Running threads hold tokens of their own, not the install token, so they keep working. The local `apps/mcp/external/stdio.ts`, when it reads its token from the file, picks up the new one on its next call.

| Client | How it sends the token |
| --- | --- |
| Desktop app | Reads `api-token` in its data dir. Before it attaches to whatever answers on the port, it asks `GET /api/auth/proof?nonce=` for an HMAC of the port and a fresh nonce, keyed with the token, so a program squatting on the port never gets the token or your secrets, even by relaying the nonce to an Omni on another port. When it starts the server, it puts a random secret in the server's environment (`OMNI_DESKTOP_PAIR_SECRET`). Before each window load it trades that secret (or the token) for a one-time nonce (`POST /api/auth/desktop-nonce`, header `X-Omni-Desktop-Secret`) and opens `http://127.0.0.1:<port>/api/auth/desktop-pair?nonce=<nonce>` in its window. The nonce works once, for 60 seconds, and only on a top-level load the page did not start (`Sec-Fetch-Site` absent or `none`). The server sets a device-session cookie, never the install token, and redirects to `/?api=<the cookie's path>`. When a request later gets 401 (after a rotation or a revoked session), the page asks the app to pair it again, at most once every 10 seconds per window. Against an older server with no nonce route (404), the app falls back to the plain `desktop-pair`. Another process on this Mac cannot pair itself without the secret or the token, and a request through Tailscale or any proxy header is refused |
| The `omni` command ([The omni command](cli.md)), `npm run setup` | `OMNI_TOKEN` or `OMNI_TOKEN_FILE`, else the install's `api-token`, which the desktop app's shim names. Inside a thread only the thread's own token |
| Threads | Never the install token. Each spawn of a thread's harness gets a token of its own (`omt_...`) in `OMNI_TOKEN`, next to `OMNI_URL`, and Omni's MCP servers (`apps/mcp/omni.ts` and the Rust `omni-mcp` behind ask, render, steps and threads) get `OMNI_TOKEN_FILE`, `data/threads/<id>/token`, so no token is written into `mcp.json`. The server keeps only its hash, takes it only from this machine, and drops it when the process exits. It acts as that thread: it cannot pair a device, open a terminal or answer a question card, and its messages are the Conductor's ([ADR 0016](../adr/0016-thread-bound-credentials.md)) |
| Web UI | Pairs once (below) or signs in with Google. Either way it holds a device session of its own in an `HttpOnly`, `SameSite=Strict` cookie, `omni_session_<port>`, never the install token. Over plain HTTP the cookie lives on a path of its own ([below](#the-session-cookies-path)) |
| MCP clients outside Omni | On this Mac, `apps/mcp/external/stdio.ts` reads `data/api-token`. Over HTTP, `/mcp` takes a Clerk access token for the linked Google account that was issued to this Omni's MCP resource or to a client you approved, or its own token, `data/mcp-token`, as a header or in the URL. See [Omni as an MCP server](external-mcp.md) |

The server serves the Web UI and its assets without the token, and they never contain it, so opening the page gets you only the pairing screen. Pairing sends the token once to `POST /api/auth/pair`, which makes a device session and answers with its id as an `HttpOnly`, `SameSite=Strict` cookie, on its own path over plain HTTP and on `/api` with `Secure` behind HTTPS. The token itself is never stored in the browser. Page scripts never see the cookie, `EventSource` streams carry it, and the browser's paired session is listed under signed-in devices, where Revoke ends it at once. A browser that already holds a live token-paired session keeps it when it pairs again, so reloading the desktop window does not add a device each time. A cookie holding the raw token, set by an older build, is swapped for a session on its first request that passes every check. The token gets to a browser one of two ways:

- Paste it from `data/api-token` into the pairing screen.
- Open a link with `?pair=<token>` after the route, like `http://127.0.0.1:4747/#/?pair=...`. `omni open --pair` prints one. The page swaps it for the cookie and drops it from the address bar. The link holds the token itself, so share it only with your own devices.

Through `tailscale serve`, set `integrations.tailscaleLogin` in `data/omni.config.json` to your Tailscale login (comma-separate several) and requests must also carry a matching `Tailscale-User-Login` header, which `tailscale serve` sets from the peer's identity. A request counts as coming through it when its `Host` is a `.ts.net` or 100.64.0.0/10 name, or when it carries any proxy header (`X-Forwarded-Host`, `X-Forwarded-For`, `X-Forwarded-Proto`, `Forwarded`, `Tailscale-User-Login`, `Tailscale-Funnel-Request`). `tailscale serve` always sets `X-Forwarded-Host` (`addProxyForwardedHeaders` in its `ipn/ipnlocal/serve.go`) and strips client-sent identity headers, so a peer that sends `Host: 127.0.0.1` is still asked for the login. Tagged nodes and other users then get a 403 even with the token. This is defense in depth. The token is the main control. The Omni Connect hostname skips this check, since its requests come through Cloudflare, not Tailscale.

The token stops other macOS accounts, other tailnet devices and anything else that reaches the port. It does not stop a web page from using a paired browser's cookie, so `apps/server/request-guard.ts` also refuses:

- a `Host` that is not loopback, a `.ts.net` name, a 100.64.0.0/10 address, this machine's [Omni Connect](omni-connect.md) hostname while Connect is on, `OMNI_HOST` or one listed in `OMNI_ALLOWED_HOSTS` (comma-separated). This stops DNS rebinding. The Cloudflare Tunnel name in `integrations.mcpPublicUrl` is not on this list. Only `/mcp` and `/.well-known` answer to it.
- `Sec-Fetch-Site: cross-site` or `same-site` on any route that acts, and any `Origin` (`null` included) that is not the host the request came in on. A page on another port of the same host (a dev server, a container UI) counts as foreign: only `same-origin`, or no `Sec-Fetch-Site` at all, passes.
- a `GET` that would start a process. Opening a thread's terminal (`POST /api/threads/:id/terminal`) and starting a channel's browser (`POST /api/channels/:id/browser/start`) take a `POST` from the Web UI; their streams only attach and answer 409 when nothing is running. An image in a PR body, a review comment or an agent reply therefore cannot start anything by being viewed. One `GET` still runs `git`: reading a thread's PRs (`GET /api/threads/:id/pr`) first checks which branch its worktree has checked out, so a PR the agent opened from a branch of its own is found. It only reads the worktree and updates the thread's branch, and starts no agent, shell or browser (a deviation from PRD #667 that Ben approved). In the Markdown renderer, an image that points at a relative path or an `/api/` route renders as `[image: alt]` text, and in PR content an image from another site shows as "Load image" from `<host>` until you click it.
- `text/plain` and form-urlencoded bodies (415), the types a page can send without a CORS preflight.

The desktop app's port check, `apps/mcp/omni.ts`, the `omni` command and curl send no `Origin`, so the `Host` and token checks apply to them. Without the token or a session, every route answers 401. The exceptions are `GET /api/auth/proof`, `POST /api/auth/desktop-nonce` with the desktop secret and `GET /api/auth/desktop-pair` with a fresh nonce, from this machine (a proxy or another machine is refused), the Google sign-in routes (`GET /api/auth/methods`, `POST /api/auth/google/start` and `POST /api/auth/google/poll`, which still get every other check above), `POST /api/hooks/github/<automation>`, which proves itself with GitHub's signature instead (see [GitHub webhooks](automations.md#github-webhooks)), and Omni Connect's `POST /api/connect/mint`, `/health` and `/redeem`, which prove themselves with the relay's signature or a one-time code and a key proof. Omni serves HTML and SVG artifacts with `Content-Security-Policy: sandbox`, so a page opened in its own tab does not run on Omni's origin.

The thread terminal opens only for the install token or a session paired with it: the desktop app's window and a browser paired by pasting the token or opening a `?pair=` link (listed with the method `token`). A shell can read `data/api-token`, so a Google, Omni Connect or iOS app session cannot open one: the Web UI still shows it the Terminal tab, and opening it shows the 403 as its error. A channel action's command runs in a login shell too, so the same rule covers adding or editing an action (including making it the setup or teardown step), running one and Run again on a run: those sessions get the same 403 on the action's row. They can still read the actions and their runs, stop a run and remove an action. Retry setup on a thread whose setup step failed reruns that step, so it takes the same credential (and so does Resume on that thread, which retries setup). Without a setup step, Retry setup only checks the branch out again and stays open. A setup or teardown step still runs on its own for a thread such a session starts or cleans up, since only the token or a session paired with it can have written its command. An automation's `precheck` is a login-shell command too, so adding one, changing its command or timeout, or moving its automation to another channel's folder or another machine takes the same credential, which a thread's own token is not; editing the rest of the automation, turning it on or off and Run now stay open, and a saved precheck keeps running on schedule. A browser paired with the token counts as one only on its own cookie path (below): its cookie anywhere else, and a signed `omni_doc` address, get 401 for any of these. To cut a device off from the terminal, revoke its session. Agents still run code, so revoking a session does not undo what it already started (see [Native app pairing](../internals/app-pairing.md#what-revoking-does-and-does-not-stop)).

### The session cookie's path

Cookies ignore ports, so a cookie on `/api` for `127.0.0.1` also goes to every other service on `127.0.0.1` the browser visits under `/api`: a dev server, a container's UI, a proxy that forwards it on. Over plain HTTP the session cookie therefore lives on `/api/k/<key>`, with 32 random hex characters per session, and the answer that pairs the browser names that path (`api` in the JSON of `GET /api/auth`, `POST /api/auth/pair`, the Google poll and Omni Connect's redeem, or `?api=` on the desktop window's redirect). The page keeps it in `localStorage`, which is per origin, port included, and sends every request under it (`apps/web/src/api-base.ts`). The server takes the key off before routing (`app.ts`), and `request-guard.ts` takes a browser session only on its own path: another port never gets the cookie, and its value alone, as a cookie or a bearer token from anywhere, gets 401.

- A tab, a frame or a download the page opens on the keyed path (`Sec-Fetch-Mode: navigate`, or `Sec-Fetch-Dest` `document`, `iframe`, `frame`, `embed` or `object`, or with no Sec-Fetch headers at all an `Accept` that names `text/html`) is sent with a 303 to the same route on `/api` with `omni_doc=` added: the session's id, an expiry 12 hours out and an HMAC keyed with the install token over that one URL. It opens only that URL, for reading, and never `/api/auth`, so an artifact that reads its own address learns no key.
- Behind HTTPS (`tailscale serve`, Omni Connect, the phone layout) the cookie stays on `/api`: it is `Secure`, so no plain-HTTP service on the host gets it. An HTTPS service on another port of the same `.ts.net` name still would.
- A browser paired before this keeps its cookie on `/api` until its next `GET /api/auth` (every page load starts with one), which gives the session a new token on a keyed path, keeps its row under signed-in devices, and drops the old cookie. The old token then stops working. A copy of it taken before the update can be moved the same way by whoever sends it first: the browser then shows the pairing screen, and Revoke under signed-in devices ends the moved session.
- A browser that loses its `localStorage` but keeps its cookies (or Safari, which clears a site's script storage after 7 days of use without a visit) shows the pairing screen again. The desktop app pairs its window by itself. Only the desktop window takes `?api=` from its address, so a link from another site cannot change where a browser's requests go.
- A link the phone layout copies to an artifact leaves the key out: it is `/api/artifacts/...`, which opens in a browser whose cookie is on `/api` (behind HTTPS).
