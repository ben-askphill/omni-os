# Threads

A thread is one task's conversation with one agent, from the first prompt through every follow-up. Threads are dated, full-text searchable (Search page) and resumable any time. Rename or archive one from its menu or with `/rename`.

A thread's menu is the same list on every surface. On desktop web and in the desktop app, open it with the ⋯ in the thread header or a right-click on the thread. On a phone, open the thread's options. It has at most ten actions in three groups. **Organize** has Pin, Mark as done, Rename, Move to folder and Archive. **Continue** has Fork thread, Reference a thread and Add an agent. **Send to** has Grok Bot, shown only when its webhook URL is set. The menu leaves out any action that does not apply to the thread right now. It has no action for where the thread runs. The Machine chip in the reply box hands a thread off or takes it over (see [Where a thread runs](sync.md#where-a-thread-runs)).

## Finding threads and clearing Needs you

On desktop web and in the desktop app, the sidebar's Running and Pinned sections list work across channels. Running lists queued threads, threads whose sub-agents still run (with those sub-agents nested under them) and threads with a delegated thread still working at any depth. It hides when empty.

A thread shows as running everywhere while a thread it delegated (a team thread and its members included) or a sub-agent it started (an Agent call, workflow, fork or teammate) still works, even after its own turn ended. That covers its sidebar row, the Inbox's Working shelf, thread lists, its channel's running count and the thread's status pill. Every thread above it shows as running too, and a team thread's working member keeps the threads above the team running. It goes back to done or idle when the last one finishes and Omni has handled its report. Background shells and monitors do not count, and neither do sub-agents left running by a stopped or failed turn. A delegated thread counts only while its own status is running or queued. A child that died stops counting once Omni marks it failed or stopped, which happens at its exit, on Stop or when Omni restarts. On your other machines, a thread that runs elsewhere shows as running from the sub-agent updates sync brings. A sub-agent there that sends nothing for 15 minutes stops counting, so a machine that went offline mid-run does not keep the thread busy everywhere.

### Status marks

Every thread carries one mark, on desktop web, phone web and the desktop app. The native iOS app keeps its own glyphs.

With **Show technical details** off (Settings > Appearance), each mark keeps its shape and color but is named with one of five words: **Working**, **Needs you**, **Done**, **Failed** or **Stopped**. A mark that says more than its word keeps its own name as the detail, in its tooltip and screen reader label ("Needs you: Usage limit"). The table below gives each mark's own name, which is what it reads with the switch on. The iOS app names its statuses the same way.

- **Shape says who has the ball.** A circle is the agent, a square is a system outside Omni (checks, a usage limit), a diamond is you, a cross or triangle is broken.
- **Color repeats it**: blue, amber, vermilion and red, with volt for done and grey for quiet states. No state depends on color alone.
- **Fill says how far along**: hollow, half, filled.
- **A small satellite dot** means the state belongs to a thread under this one.
- **Motion**: a mark sends out a halo while the agent's own turn works, and breathes slowly while it waits on other work. Everything that waits on you, is broken or has settled holds still. Nothing spins. With reduced motion on, every mark holds still and the shapes still tell the states apart.

| Mark | State | When |
| --- | --- | --- |
| Grey dashed ring | Queued | The thread waits for a free slot |
| Half-filled blue circle, halo | Starting | Omni prepares the thread's folder, or the open thread's turn has not shown anything yet |
| Filled blue disc, halo | Running | The thread's own turn runs |
| Blue dot inside a thin ring, halo | Running a tool | The open thread has a tool call with no result yet. Lists show Running, since they do not load a thread's rows |
| Blue disc with a satellite, breathes | Waiting on crew | Its own turn ended and a delegated thread or sub-agent still works |
| Filled amber square, breathes | Checks running | A pull request has checks in progress |
| Half-filled amber square, breathes | Resumes at reset | A usage limit stopped it and it continues by itself when the limit resets |
| Hollow amber square | Usage limit | A usage limit stopped it and nothing is scheduled |
| Filled vermilion diamond | Waiting on you | The agent asked you a question |
| Vermilion diamond with a satellite | Crew waits on you | A thread it delegated asked you a question |
| Half-filled vermilion diamond | Ready for review | It finished and its branch has an open pull request that is not a draft. Shown where the pull request is loaded: channel thread lists, the thread's status pill and its quick card. Sidebar rows show Done |
| Hollow vermilion diamond | Message held | A message of yours was held back or may not have arrived, and waits for you to send it again or drop it |
| Red cross | Failed | The turn failed |
| Red cross with a satellite | Crew failed | A thread it delegated failed |
| Hollow red triangle | Setup failed | Omni could not prepare the thread's folder |
| Volt disc with a tick | Done | The turn finished |
| Grey bar | Stopped | You stopped the turn |
| Small grey dot | Idle | It never ran, or it was imported |

A thread you marked done shows a plain tick instead.

A thread with several [agents](#agents-in-a-thread) shows their avatars in place of its mark while any of them works or waits on you: the one asking you first, in the Needs you ring with the Needs you diamond on it, then the ones working, in the Working ring. It shows two faces at most; with more, it shows the first and a count (+2). A red dot beside them means an agent failed while another still works. Hover it, or read it with a screen reader, for who does what. The desktop thread lists, Inbox cards and the Overview dashboard draw it; on a phone, the thread's row says it on a second line instead ("Builder asks you · Designer working"), in channel lists and Activity alike. Once every agent is idle, the thread shows its one mark again.

While Running is open, a thread in it has no second row under its channel or folder, so clicking it highlights one row. Fold Running and its threads show under their channels again. A pinned thread still shows under its channel too. For the latest threads by activity, use the Inbox view (or the Inbox disc when [Channel rail](configuration.md) is on) or Cmd-K.

A thread that delegated work, such as a Conductor thread, shows the threads under it as a tree below its row: in the sidebar, on its Inbox card and on its phone Activity row. Each child row has a status mark, the harness logo and the title. Hover it for the model. When the job's children sit in more than one channel, each row also names its channel. A job whose threads work outside its own channel also shows those channels as overlapping avatars, once each, in the order it handed the work out, finished threads included. On its Inbox card they take the place of the channel's avatar, its own channel first. In the sidebar they start the row's second line, without its own channel, which the row already shows. Past four channels the last disc is a +N chip. Hover them for every channel by name; they have no click of their own. A phone Activity row has no hover, so it gives them a line of their own above the channel's name, with every channel written out beside the discs. A team is one thread, so it has one row in the tree, its members' avatars on it ([Teams](#teams)). A team made before teams became one thread keeps its tree: its members sit under their lead. Running sub-agents nest under the row of the thread that runs them only while its job is at work: on the Inbox's Working shelf, and in the sidebar under a job that is running. They leave when they stop, and a sub-agent left behind by a stopped or failed turn never shows. Open, the tree lists the threads that need you, failed or still run, then the three newest finished ones and an **n more done** row for the rest. The row's second line (the branch, or "4 delegated", or "Team of 7" for an older team) ends in a tally of needs you, failed, running and done with a chevron that opens and closes the tree. The tree is open while anything under the job runs and closes itself once all of it finished. Closed, it still lists the threads that need you or failed, with an **n more** row. A failed thread keeps its row after you open it, until you mark it done. If you open or close it yourself, that holds until the job moves between running and finished; then it opens and closes by itself again. On the Inbox's Working shelf (desktop and phone web), a fold button left of the shelf's chevron closes every card's tree at once, and opens them all again once all are closed. It saves the same choice as each chevron, so a chevron still works on its own and the button turns back to Collapse all as soon as one tree is open. The native iOS app has no such button. The sidebar and the Inbox (desktop and phone) keep their own open state on this device. In the sidebar, a delegated thread also keeps its own row in its channel. In the Inbox it shows only under the thread that delegated it. The Conductor's channel page still nests them under their parent, with expand and collapse, and the parent's Details tab lists them at the agents card.

Each section folds on its own and remembers its state on that device. On desktop web and in the desktop app, the Conductor section starts folded, because its folders hold every job. Clicking it opens its page without unfolding it. Click it again on its page to unfold it.

The sidebar's Inbox view, toggled against Projects, lists pinned threads first, then four shelves in a fixed order, each with its count: Needs you (a question, a failure or a usage limit), Finished (turns that ended, bold while unread), Working and Done. Needs you and Finished show the latest back on top and never fold. Working and Done fold and remember their state on that device. The phone's Activity tab still shows Needs you and Finished as one list. Under its title a card names the machine the thread runs on now, or last ran on, and while it runs, how long the current turn has gone ("MacBook Air · 12m", counted from your last message, the same as the thinking line). On desktop web and in the desktop app, hover the line for the machines it ran on before a handoff or Take over, and its branch. A thread from before sync, or on a single machine without sync, shows its branch there instead. Channel thread lists and the native iOS Activity list still show the branch on that line. A card's status matches what Home says about the thread. It reads Working while sub-agents still run after a turn that ended done, and Stopped for a thread you stopped, even while a background task from its turn still runs. The check on a card marks it done, and the undo on a Done row puts it back. In the channel rail the same shelves fill the list panel from the Inbox disc (and from Go > Inbox in the desktop app), and the page beside it is the Overview dashboard until you open a thread. Overview's Working count is the Inbox's own, so the two never disagree.

On a phone, Activity shows the same list as the Inbox view, and a channel splits its folder and ungrouped threads between Active and Recent. Threads that delegated work there show the same tree under their row, with sub-agents shrunk to one "n agents running" row and each child's time instead of its model. The native iOS app's Activity tab shows the same tree and asks the same question before Done.

**New thread** in the sidebar opens a composer in the channel you are in. In the desktop app, File > New Thread and Cmd-N (Ctrl-N off the Mac) do the same. From inside a thread, it uses that thread's channel. While the channel rail shows the Inbox, it opens the Overview's composer beside it instead, set to that channel, so the thread you start opens in the Inbox too; `/new`, an Open items **+** and the follow-up thread's edit button do the same. On a phone, a New thread chip above the reply box does the same.

Overview (`#/`, and the rail's Inbox disc, beside the Inbox list), on desktop web and in the desktop app, is a dashboard for Today, 7 days or 30 days, and that device remembers the range. Under the New thread composer, the Start in chips offer the four channels with the most threads started in the range. Four tiles count Needs you (by what holds each thread up), Working (the Inbox's Working shelf, with the busiest harness's slots), Unread and Done (marked done in the range). Each opens its list in place, at `#/?list=needs`, `running`, `unread` or `done`.

Once another machine syncs with this one, a Machines row under the tiles has a tile per machine, this one first. A tile shows the machine's running threads (and queued, delegated and Needs you), each busy harness against its slots, and, for this machine only, in-process sub-agents, since only this machine sees its own processes. Under those are a CPU bar and a RAM bar with their numbers. The CPU bar's tooltip has the load average and core count.

- CPU is the busy share of all cores over the last 5 seconds, from the change in `os.cpus()` times.
- RAM is memory in use against the total, as the OS counts it. On macOS it is app memory, wired and compressed from `vm_stat`, matching Activity Monitor's Memory Used. Node's free memory there counts only free pages, so a full file cache would look like a full Mac. On Linux it is MemTotal less MemAvailable from `/proc/meminfo`, matching `free`. Other platforms get no RAM bar.
- A stat a machine cannot measure is left out, never shown as zero.

A machine samples only while someone watches. It samples every 5 seconds while a client on it shows the tiles on screen (a hidden tab, a minimized window or a phone tab under another one stops asking, and asks again on return), or while another machine that shows them has asked through sync in the last 90 seconds (kv `machine-watch.<id>`, renewed every 45 seconds). Omni ignores a watch stamped over five minutes ago, such as one a machine catches up on after sleeping. While sampling, the machine sends its sample every 15 seconds (kv `machine-stats.<id>`, which keeps the time it was taken).

Another machine's sample shows grey with its age ("Sampled 4m ago") when it is over a minute old, when Tailscale reports that machine offline, or while sync here is not live. A machine on an older build says it has sent no stats yet. The thread numbers come from the thread rows sync carries and refresh with the feed, and the bars move with the feed's samples. A machine Tailscale reports offline shows a dash, when it was last seen and what it last reported. While sync here is paused or failing, the other machines' tiles say how old their numbers are. A tile opens the Working list narrowed to that machine (`#/?list=running&machine=<id>`). That list has every thread the tile counts, delegated threads and team members included, even though the Inbox's Working shelf lets a job's row stand for them. The phone's Activity screen shows the same tiles in a strip you scroll sideways. The Conductor reads them with its `machines` tool, stats included with each sample's age, after waiting a few seconds for fresh ones.

Usage sums tokens and cost from the Claude Code and Codex session logs on this machine (`~/.claude/projects`, `~/.codex/sessions`). It counts all sessions, not only Omni's, and adds Cursor's billed usage where Omni can read its dashboard, the way T3 Code's usage view does. Cost is LiteLLM's list price per model, or what the provider billed. Cache hit, tokens per session and cache savings are computed from the totals shown. The first read of the logs runs in the background and the section fills in as it goes. After that, Omni reads only what changed.

Below Usage come Needs you, Busiest channels, Pull requests (open, yours, with CI checks, merged from a thread's branch in the range) and the automations still to run today. When you come back to Overview, it shows the numbers it last read at once and asks the server again only when they are over five minutes old. The header says when they were read, and Refresh reads them now. A refresh that fails keeps the numbers on screen and says why. The Conductor reads the dashboard's other numbers with its `insights` tool. On a phone, Overview stays Activity.

Needs you holds unread results and threads waiting for you to act. A delegated thread, or a member of an older team, that fails, at any depth, brings the thread you delegated from to Needs you instead, the way its question does, so one failure counts once. It stays there until you open the failed thread or mark it done. Review on a phone card opens the failed thread. Opening a thread reads the result it shows, so a newer result stays unread. **Mark as done** clears any of those reasons without archiving the thread or changing how its last turn ended. The thread stays in its channel and folder with a grey check, a muted title and a Done chip. **Mark as not done** brings back its unread result and blockers. A new message, a run starting or Retry setup clears done. The server keeps the flag and syncs it between Macs, so desktop web, the desktop app and the phone show the same threads as done. You cannot mark a running or queued thread done. Marking a job done while a thread under it still runs, failed or waits on you asks first, and says what is left. Once everything under it finished, it is one click.

On desktop web and in the desktop app, use the check on a Needs you row or an Inbox card, the check in the thread header, or the thread's menu. The thread header keeps only the agent the thread runs as (beside the channel crumb, left out on the Conductor's own threads), the channels its delegated threads work in, the context meter, Mark as done, the status, the thread menu (⋯) and the quick-card and panel toggle. Pin, Reference and Send to Grok Bot are in the menu. Hand off and Take over are on the reply box's Machine chip. On a phone, use the check on an Activity row or Thread options. The Conductor can use `mark_thread_done` when you ask it to.

## Quick asks

A quick ask is a question answered where you asked it, not a thread to manage. Ask from the desktop app's Quick Prompt (Return), or the phone web's and the iOS app's New screen with Ask picked (Task starts a thread as before).

- It runs on Auto unless you pick a model, with read-only tools: it reads files in the channel's folder, searches and fetches the web and reads connectors, but cannot edit files, run commands, use a browser or delegate. Hermes and Cursor Cloud cannot run one (409), since Omni takes those tools away on this machine.
- It gets no charter, worktree, folder or task id (its `workspace` is `read`, or `none` in a channel with no folder), and stays out of the sidebar, channel lists, the Inbox and notifications. Recent asks lists the last 7 days (`GET /api/threads/asks`).
- Keep as thread lists it as an ordinary thread where it is, still with read-only tools. Make it a task starts a task thread in the same channel, with its own worktree and full tools, whose first message carries the questions and answers so far (`POST /api/threads/:id/promote` with `to: keep` or `task`).
- When the agent finds the ask needs real work, it answers `TASK: <title>`. Omni shows "This needs a task" under the answer and highlights Make it a task, which then takes that title. Only you start the task: text the agent read (a page, a file) cannot start one by writing a TASK line.
- Other code starts one through `startQuickAsk` (`apps/server/quick-ask.ts`), or `POST /api/threads` with `quick: true`.

## The composer

- A new thread follows the channel and crew defaults until you pick a model or effort for that draft. When no default is set, Auto picks from the first prompt. The Conductor agent's charter is Auto, and a saved #conductor channel default still wins. See [Harnesses](harnesses.md#auto).
- `/` opens the menu of skills, slash commands and MCP prompts for the thread's harness. In a thread's reply box, `/model`, `/effort` and `/fast` open the model pill, and what you pick applies from the next turn.
- `@` mentions artifacts and repo files. In the Conductor (any thread whose agent has the Omni tools), and in the composer that starts a Conductor thread, it lists your synced machines first, shown as an inline pill once picked, this one included, each with whether Tailscale sees it up, on desktop web, the phone and the desktop app. See [Send a task to a machine](sync.md#send-a-task-to-a-machine). In any thread the `@` menu opens on its **Agents** tab, beside **Machines** and **Files**, and an agent you pick joins the thread ([Agents in a thread](#agents-in-a-thread)).
- **Templates** are ready-made jobs: a client question with sources, a meeting agenda, meeting recall, a decision record from a meeting, and a ticket turned into a proposal and a comment. They sit under Templates in the `/` menu on every harness, and as chips under an empty new-thread box on desktop web, phone web, the desktop app and the iOS New screen. A chip puts `/<name> ` in the box; type what the job is about after it. Omni sends the template's instructions with your text in place of the command, and the transcript shows what you typed with the template as its pill. A harness skill or command with the same name wins over a template. The Shopify ones (a CRO audit, Connect a store) show only while the Shopify add-on is on. Settings > Threads > Templates lists them. To add your own or change one, put a Markdown file in `data/templates/` (the format is in [`templates/README.md`](../../templates/README.md)); a file with a shipped template's name replaces it. The Conductor lists them with `list_templates`.
- After a finished turn, Haiku suggests your likely next reply. Tab fills it in, and `OMNI_SUGGESTIONS=0` in `.env` turns it off. That call, and the ones that title a new thread or propose a follow-up, run in a private folder under Omni's data dir, not the shared temp dir.
- With **Open items card** on (Settings > Threads, off by default), when a finished turn leaves something for you to resolve (a question it asked, a decision it left to you, or a blocker only you can clear), an **Open items** card under the transcript lists up to five of them. Type an answer or tap one of a decision's options, then **Send answers** sends every answer as one reply. **+** opens a new-thread composer with that item as the first prompt (New thread on phone web and in the iOS app), **x** on an item dismisses it, and **x** in the header dismisses the card. Desktop web, phone web, the desktop app and the iOS app all show it. Any reply clears the card, and the next turn lists whatever is still open. A Haiku call of its own finds them, separate from the reply suggestion and the follow-up thread, and `OMNI_SUGGESTIONS=0` turns all three off. With the setting off that call never runs, so nothing is found or kept, and the reply reads the same either way. The setting is kept by the server and syncs to your other machines. Delegated threads report to their parent instead, so they get no card.
- An **Open PR** control appears in the composer next to the machine and model pills when three things hold: the agent's last reply asks whether to open a PR (open, create, raise, file or submit a PR or pull request), the thread is idle and its branch has no PR yet. On phone web and in the iOS app, it is a chip next to the machine chip. It sends the same open-PR prompt as the panel's Open PR button, reads **Opening PR** while that turn runs, and goes away once a PR exists or you reply.

## Sending while a thread is busy

| Mode | What happens |
| --- | --- |
| Steer (default, Enter) | Omni writes it to the CLI now. The agent reads it at its next step (after the running tool) and keeps going |
| Queue for after this turn | Omni holds it and runs it as a new turn once the current one ends |
| Interrupt and send (Cmd/Ctrl+Shift+Enter) | Stops the current step, then runs the message |

With Show technical details off the three modes read **Add to this**, **Send when it finishes** and **Stop and send**. Cmd/Ctrl+Enter adds a newline. Pending messages show under the live output and enter the transcript at the point the agent read them. A queued message has **Steer now**, which sends it into the running turn instead of waiting for the turn to end. Cursor Agent and Cursor Cloud cannot steer, so they lack it. While a turn runs and the reply box is empty, the send button turns into **Stop**. Stop (or Esc) stops the turn but keeps the process and its context. Steers already sent still run, and Omni records queued ones as "Not sent". Omni kills a CLI that does not stop within `OMNI_INTERRUPT_GRACE_MS`. Only turns in progress count toward `OMNI_MAX_CONCURRENT`; warm idle processes do not.

On Cursor Agent and Cursor Cloud, messages sent during a turn wait for the next turn. A model, effort or harness switch picked during a turn also makes messages wait for that switch, even on a harness that can steer. See [Switching mid-thread](harnesses.md#switching-mid-thread).

- To start a separate linked thread with its own session and checkout, use [Fork thread](harnesses.md#continuing-on-another-harness): the branch icon in the reply box, under + on a phone, or the thread's menu.
- To attach another thread without forking, use [Reference another thread](#point-the-agent-at-another-thread) in the header.
- To move a running or idle thread to another machine, or bring one your other Mac holds here, use the [Machine chip](sync.md#where-a-thread-runs) in the reply box.

To attach files to a message, use the paperclip, drag and drop, or paste. Omni saves them in `data/threads/<id>/uploads/` under their original names and gives the agent each one's absolute path. Images small enough for the API also go in as image blocks. `OMNI_MAX_UPLOAD_MB` caps a single file.

To continue a thread in a terminal or Claude Desktop, run `cd <cwd> && claude --resume <session id>`. The thread's Details panel has a copy button for it. Check there first that the session is no longer warm, so two processes do not write the same session.

## The thread panel

On desktop web and in the desktop app, a thread opens with a compact **quick-actions card** beside the transcript, not the full inspector. It takes a column of its own once the thread itself is 768px wide or more; in a narrower window it floats over the transcript's top right corner instead, and **Hide quick actions** in the header puts it away. The card shows the machine (with a copy-path button), working directory, harness and model, run state (live or cold session), and branch. Cursor Cloud threads get Open in Cursor instead of the path. A thread with no branch shows one muted "No branch" row.

**Owner** and **Agent** are two separate rows. Agent is the agent doing the work, like Builder, or a muted No agent; the harness and model keep their own row. Owner is the person the work is for, You until someone else is named. Press **Change** on the Owner row to name someone, and clear the name to make it yours again. A delegated thread starts with the owner of the thread that delegated it, and the Conductor's `delegate` tool takes an `owner` too. A thread owned by someone else shows "for <name>" after its channel on its Inbox card and its row in the thread list (desktop web, phone web's Activity and Channels, and the iOS app). Phone web's Details screen has the same two rows, with Agent in place of its old Agent row. The owner syncs to your other machines, and the newer edit wins.

**Lineage** sits under All details whenever the thread came from another one or delegated any: a From row back to the thread that delegated it, then each delegated thread still at work with its harness logo, a live status mark and how long its run has gone. The heading counts the running ones (Lineage · 3 running). Finished ones fold under **Previous agents** with their count, newest first, and open with a click. Every row opens its thread.

**Show technical details** (Settings > Appearance) only changes which rows the card lists; the card opens either way. Off, it keeps the machine, Owner, Agent, the AI app, the run in plain words, Files, All details, Lineage and any PRs, and leaves out the task id, working directory and copy button, the model id, the account and plan, and whether the session is live or cold. A channel with a repo keeps its branch row and the Pull requests section with the switch off; without a repo they show only once the thread's crew opened a PR.

**Pull requests** at the bottom lists the PRs from the thread's branch and the ones its delegated threads opened, open ones first, each with its number, title and state (open, draft, blocked, merged or closed). A Conductor thread lists its crew's PRs even with no branch of its own. A row opens the PR's page in Omni and the arrow beside it opens it on GitHub. The card shows five; the heading and **N more** open the PRs tab. With none, the section says No PRs yet. The other rows open the inspector on their tab, and **All details** opens it on Details. The inspector replaces the card and never sits beside it. The header's panel button switches between the card and no panel, and with the inspector open it goes back to the card. The device remembers card or no panel; every thread opens on the card even if you left the last one on the inspector. Only a click opens the inspector: a card row, All details, an artifact link or a delegate count. A new artifact does not.

**Progress** is a second card under the quick card when the thread has a step list: the newest list the agent posted with `set_steps` or its harness keeps as a plan (see the step line below). Done steps are muted, the step it is on has a status mark and says what it is doing now, and the rest wait below. Phases Omni groups the calls into do not count, so a thread with no list shows no card. The X closes it for that list on this device; a new list, or one in a later turn, brings it back.

On a phone, the same card is a popover from the header's panel button, with Progress under it. The phone does not remember it, because it would cover most of a 390px screen. Tapping outside closes it, and rows open the matching thread screen.

The inspector's tabs are Details, PRs, Files, Changes, Browser, Terminal and Actions, and the desktop app adds Web. Actions and the diff are only in the inspector, not on the quick card.

**Details** starts with the branch card for a thread on its own branch. It shows the branch, its PR with what decides whether it can merge (checks, conflicts, review), and the files changed. The step the PR needs next is a small button at the end of the PR's row. A PR that cannot merge says why on its row (Has conflicts, N checks failing, Draft, Checks running), and while checks run or it is a draft the row has no button. Merge asks first: it opens a confirm under the row that says what the merge does, with **Cancel** (focused) and **Squash and merge**. Escape closes it, and a refusal from gh shows inside it so you can try again. The steps are:

- **Open PR** while there is none.
- **Fix conflicts** or **Fix checks**, each of which asks the agent and queues mid-turn. After the prompt, Fix checks also sends up to five failing checks with their links and log tails, or the prompt alone when gh cannot read them.
- **Merge**, which squash-merges in place and deletes the branch, with the same settings as the phone's merge slider. The PR page still has the full merge card for other merge methods, with **Auto-merge** on the same row ([Auto-merge](#auto-merge)).

Each channel sets what Open PR, Fix conflicts and Fix checks ask the agent, under **Branch steps** in its settings (desktop web, phone web and the iOS app). For example, "use the pr-writer skill and the repo template". An empty field sends the built-in prompt, which it shows greyed out. The prompts sync to your other machine with the rest of the channel.

From the click until the turn ends, while that step's prompt is queued or its turn runs, these show **Opening PR** (or the matching label for Fix conflicts and Fix checks) with a pulsing dot (a spinner in the iOS app): the PRs tab, the Details branch card, the phone web PR view, and the iOS PR screen and its composer chip. A step whose message was parked (`recovered` or `uncertain`) stops showing it. The button says why it did not start, and the next press resumes that parked message. On a thread another machine holds, a forwarded Open PR, Fix conflicts or Fix checks stays in the pending rows until that machine takes it, on desktop web, phone web, the desktop app and the iOS app ([Sync](sync.md#run-a-thread-on-another-machine)). The PR and changes rows open their tabs.

A thread that delegated work, such as a Conductor thread, gets a second card with the open PRs its delegated threads opened, one row each. A PR that can merge has **Merge** at the end of its row, with the same confirm. One that cannot says why in its place: Has conflicts, N checks failing, Draft or Checks running. A server that cannot read a PR's checks leaves its Merge in place, and gh refuses a merge GitHub would block. The thread gets this card even with no branch of its own, and a merged PR leaves the card (the PRs tab keeps it). Under the cards, the agents card shows the thread's lineage (the thread that delegated it, and the thread it continued from or in), what runs now, and its finished delegated threads under **Previous agents**. MCP servers take one line, with their names behind its arrow.

**PRs** lists every PR from the branch with its checks, conflicts and review state, the next step, **Open a new PR** when none is open, and [Watch PR](#watch-pr). A thread that delegated work, such as a Conductor thread, also gets **From delegated threads**, which lists the open and merged PRs opened by the threads under it, teams included, oldest delegation first. Each row shows the PR, the task and thread it came from, and its state. Clicking a row opens the PR, and the message icon beside it opens the thread. The tab shows this list for a thread with no branch too.

On a phone (phone web and the iOS app), Thread options lists Details first and the PR screen second. A thread with delegated PRs gets that PR entry without a branch. Without a PR of its own, its PR screen shows the first open delegated PR with the merge slide and a row that opens the delegated thread. Tap a delegated PR in the list below to show that one instead.

A PR page opened from the PRs tab keeps its header short: the back link with **GitHub** and **Ask builder to review** beside it, the title, one line of state, author, branch, checks and line counts, and a **From** line that links the thread that delegated the work and the thread that opened the PR. Under the header sits the merge card. It leads with where the PR stands (**Ready to merge**, **Has conflicts**, **1 check failing**, **Still a draft**, **Changes requested** or **Checks running**) with **Auto-merge** beside it, then lists what the merge needs, one row each: conflicts with the base branch, checks (with **Rerun failed checks** on that row), review and draft. Under the rows sit the merge method (Squash, Merge commit or Rebase), Delete branch and a merge button named for the method (**Squash and merge**, **Merge commit** or **Rebase and merge**), then one sentence on what the merge does. The phone keeps its slide instead of the button. The tabs are **Conversation**, **Checks** and **Changes** (the diff, file by file, with each file's counts in its header). **Ask builder to review** (and Fix conflicts when it asks for a review) opens that work under the nearest Conductor ancestor of the thread that owns the PR's branch, or under that builder when there is no Conductor. That keeps the review and its report with the original job. A PR with no clear Omni origin, or a fork PR, gets a new standalone builder instead.

**Rerun failed checks** shows on an open PR's page (desktop, on the merge card's checks row), the phone web PR view and the iOS PR screen while a failing check is a GitHub Actions job. It runs `gh run rerun --failed` for each failing workflow run, with no agent turn, and says in place how many runs started again or why none did. Omni leaves alone a failing check from outside GitHub Actions, such as a commit status or another app. The Conductor does the same with `rerun_failed_checks`.

## Running subagents

The Details tab's agents card lists them under **Running**. That is every agent the thread started itself that is still working, such as an Agent call, a workflow, a fork or a teammate, with how far it got (in the background, its tool calls and the last one), its kind and how long it has run. Click one to scroll the transcript to the call that started it, however far back. While another tab is open, the Details tab shows how many run. On a phone, the list is at the bottom of the thread's options sheet and in its Details screen. Background shells and monitors are not listed. Delegated threads that still run are listed under Running too, and finished ones under Previous agents. Their own agents show in their own thread.

Claude Code reports its agents itself. Omni maps Codex (multi-agent spawns), Cursor Agent (its task tool) and Hermes (`subagent.*` events) onto the same list. Cursor Cloud reports no sub-agents.

## Context window

The ring in the thread header shows how full the thread's context window is. Click it for what fills the window and **Compact**. On a phone, it is the **Context** row in Thread options. The ring moves on every model call while a turn runs. Once the turn ends, Omni keeps that last reading, so an idle thread still shows its level after Omni restarts, and on your other machines once it syncs.

**Compact** works on an idle thread too, including one with no process running: Omni starts the session again to run the harness's own `/compact`, and the ring drops when it finishes. After a long idle the provider's prompt cache has expired, so that compaction reads the whole conversation at full price. Compact waits while a turn runs. Claude Code takes an optional line on what the summary should keep; Codex compacts without one. Cursor Agent shows its estimated level with Compact off, since it has no compact command. Hermes and Cursor Cloud report no context window, so they show no ring. Starting a thread over with fresh context or on another harness clears the level until the next turn. With Show technical details off in a channel without a repo, the header ring shows only from 70%; the phone's Context row always shows.

## Goals

On Claude Code, `/goal <condition>` keeps the thread working until the condition holds. A line under the transcript shows the goal: **Pursuing goal** while a turn works on it, **Goal set** while it waits, and **Goal complete** once a turn ends with it met. It also counts how often Claude's check found the condition unmet. **Clear** sends `/goal clear`. A `/goal` message never steers into a running turn: it queues, and a new goal or a clear while one is active stops the turn first. A met goal leaves the line when your next message reaches the session, and any goal goes away when the thread starts a new session. While the thread works toward a goal, its status reads **Goal**, not Running. Claude Code has no pause or resume for goals. The goal stays on the machine that runs the thread and does not sync. Desktop web, phone web and the desktop app show the line; the iOS app does not. Codex, Cursor Agent, Cursor Cloud and Hermes get no goal line.

## Point the agent at lines of a diff

In a thread's Changes panel (desktop web, phone and the desktop app), click a line number to pick it, and shift-click another in the same hunk to pick the lines between. On a phone, tap a line, then tap another. Write a note and press **Add to message**. The lines and the note go into the reply box as a chip, next to whatever you have typed. Click a chip to see what it holds, or x to take it out. A message can be just chips.

The agent gets the lines as you saw them, with the path, the line numbers, the commits they were compared at and your note. Omni tells it when the file has changed since you picked them. Your message in the thread keeps the lines exactly as you sent them. It is feedback for this thread only, not a GitHub review. Cursor Cloud threads, and Hermes threads from before remote agents, have no Changes panel. A remote agent is told the file is on your Mac. How it works: [Message context](../internals/message-context.md).

### Review notes

**Pin note**, next to Add to message, keeps the note on the lines instead of sending it (desktop web, phone web, the desktop app and the iOS app). The note stays in the diff under its lines, survives a reload and syncs to your other Mac. Edit it with the pencil, resolve it with the check, or delete it with the bin. Resolved notes fold into **Resolved** above the diff, kept as history.

When the diff changes, a note follows its lines. Omni looks for the same text nearest where you pinned it, and marks the note **Moved** when it finds the text somewhere else. When the lines are gone, the note is listed above the diff as **Outdated**, with the lines you pinned it to. **This turn** shows only the notes on lines that turn changed and counts the rest.

**Send open notes** sends every note that is neither resolved nor sent yet as one message to the thread, each with its lines, and marks them **Sent**. Editing a sent note opens it again, so the new words go with the next send. One send carries up to 40 notes.

**Send to**, under the button, picks where that message goes:

- This thread, the default.
- One of the threads it delegated to.
- **New delegate**, which starts a thread under this one in the same channel, with the same harness and model and the notes as its first message. A new delegate runs on this Mac and, in a worktree channel, branches from this thread's branch (committed work only). Its report comes back to this thread like any delegate's.

Either way the notes stay on this thread, marked **Sent**. The picker is the same on the desktop, the phone and the iOS Changes screen. The Conductor reads a thread's open notes with `list_review_notes`.

## Point the agent at terminal output

In a thread's Terminal tab (desktop web and the desktop app), select output with the mouse as usual. A panel opens at the bottom of the terminal. Write a note and press **Add to message**, and the selected text goes into the reply box as a chip, next to whatever you have typed. Copy and paste work as before, and Esc in the panel clears the selection. On a phone the terminal is read only and you can't drag over it. Tap a line, then tap another to take the lines between, then press Add to message. A message can be just chips.

The chip is a snapshot of the text, the directory the shell started in, the shell's process id and the time you added it. It does not change when the terminal scrolls on, restarts or the shell exits. The agent gets the text as plain text and is told it was not run. Omni drops escape sequences when you add it, and output that holds Omni's own block tags can't pass for them. A chip takes up to 200 lines and 8,000 characters. Omni refuses more rather than cutting it. How it works: [Message context](../internals/message-context.md).

## Point the agent at part of a web page

In a thread's Browser panel (desktop web, the desktop app and the phone's Browser screen), or in the desktop app's Web tab, press **Annotate**. It stays on until you press it again, Done or Esc, and the page stays live under it:

- **Hover** over the page (desktop web and the desktop app) to see what is under the pointer. Omni outlines the element, and a tooltip shows its tag, id and classes, its size, its path in the page (`body › main#cart › button#go`) and a few computed styles (color, background, font, display, padding, margin, z-index). The page still gets the pointer, so hover menus open as usual. Scrolling and typing go to the page too.
- **Click** an element to pick it, or **drag** over an area. On a phone, tap or drag. Omni takes a screenshot at once, so what you send is the page as you saw it, and the outline follows the page when it scrolls.
- **Hold ⌥ Option** to click the page itself while Annotate is on, for example to open a menu before you pick an item in it.

A card at the bottom shows the screenshot of what you picked, the element's details and a note field.

- **Send** sends it to the thread at once, with your note as the message and the annotation attached.
- **Add to message** puts it in the reply box as a chip instead, with the note on the chip, so you can add more before sending.
- **Draw** opens the screenshot in the markup toolbar (select, pen, shapes, text, color, line width, undo and delete) with your pick already marked. Add to message there adds the marked-up screenshot.
- x clears the pick. Esc clears it, then turns Annotate off.

A pick never clicks, navigates or changes the page. The desktop app's Web tab is your own browser, and Annotate works the same way on it. The agent gets the same annotation, though it still can't see or drive that browser.

If the page navigates, the tab changes, the browser is resized or the page scrolls while Omni takes the screenshot, Omni says so and offers **Try again**. That way the area is never drawn on a different page than the one it describes. Omni keeps the screenshot as a file in the thread, so the chip survives a reload (the web keeps unsent chips in this browser) and shows in the sent message. The agent gets the page's address and title, the viewport, and the area in page pixels, with the screenshot as an image. Claude Code and Codex see the image. Cursor reads the file from the path it is given. An agent on another machine (Hermes, Cursor Cloud) is told the file is on your Mac. If the screenshot has gone missing, the message says so instead of skipping it.

**Picking an element.** A click or tap, as opposed to a drag, asks the page what element is under that spot. Omni marks its box and, under **Details**, shows its tag, selector, text, a short excerpt of its markup and its computed styles before you send it. The agent gets that same excerpt, quoted as data from the page. The excerpt is capped at 600 characters of text, 2,000 of markup and four parent tags. It never holds what you typed into a field, and it leaves out a link's query and fragment. Omni says so when the page has moved on since the screenshot, the spot is in a frame from another site, or the page cannot be read. The screenshot and any area you drag still go with the message, without the element. How it works: [Message context](../internals/message-context.md).

## Mark up an image file and send it back

In a thread's Files tab (desktop web and the desktop app), open an image and press **Annotate and send** in its header. The same markup toolbar opens over the image, starting on the rectangle: pen, rectangle, ellipse, arrow, line, text notes, color, line width, undo, delete and **Clear**. Click with the text tool to pin a note to that spot. Write what should change under it, then press **Send**.

The thread gets a new message from you with the marks flattened into a PNG attachment. The message lists the text notes, numbered, and every other mark, all in the image's own pixels. An image from **From delegated threads** goes to the thread that made it, and **Send to** switches it to this one. When that delegated thread has been idle past the prompt cache's hour, Omni says so and the button reads **Wake and send**; **Send to this thread instead** keeps it asleep. The phone layout has no Annotate on files.

## Point the agent at another thread

In the thread's header, press the **Reference another thread** button (the speech bubble next to the context meter on desktop web and in the desktop app). On every surface, **Reference a thread** in the thread's menu does the same. Archived threads hide the button. Search by title or channel and pick a thread. It goes into the reply box as a chip, next to whatever you have typed, and x takes it out. The search lists this channel's threads. **All channels** lists the others, and Omni attaches a thread from another channel only when you pick it there, marked "other channel". When two threads share a title, the start of their id tells them apart.

You can also reference a thread as you start a new one. In the new-thread composer, press the speech bubble next to the paperclip (desktop web and the desktop app), or the speech bubble next to **+** in the phone's New sheet. The same picker opens, searching the channel the new thread starts in, with **All channels** for the others. Each pick becomes a chip over the box, and x takes it out. **Start** sends the chips with the first message, so the new thread's agent can read those threads from its first turn. If you change the composer's channel after a pick, the chips stay and go as references to the channel each one names. A thread you start on another machine cannot carry a reference yet, so Omni says so and starts nothing. Grok Bot takes text only, so the button hides while it is picked and a chip already there blocks the send. The phone's New sheet drops its chips when it closes, as it drops its text. The native iOS app has no reference picker yet, in a new thread or a reply.

The chip holds the thread's title, channel and id as they were when you sent the message, so renaming or archiving it later changes nothing in a sent message. Click the chip to see them, and **Open thread** to go there. Attaching a thread does not message it, start it or change it, and none of its messages go into yours. The agent is told the thread exists and reads its history only when it needs to, with the `read_referenced_thread` tool, one page at a time (at most 100 messages and 60,000 characters). The tool reads only a thread you attached to a message in the calling thread, and says so when that thread is gone. Claude Code, Codex, Cursor and the Conductor have it. Hermes and Cursor Cloud threads run elsewhere, so they get only the reference. A message can be just chips. How it works: [Message context](../internals/message-context.md#thread-references).

## Agents in a thread

A thread can hold more than one agent ([ADR 0019](../adr/0019-group-threads.md)). The agent it started as is its **lead**. Any other agent you seat is a **member**, with a session of its own in this thread. Desktop web, phone web and the desktop app have it; the iOS app gets it later.

- **Seat an agent.** Type `@` in the reply box and pick an agent from the **Agents** tab, or pick **Add an agent…** in the thread's menu or the member list. The agent joins with a "Designer joined" line. Add an agent starts no turn: the agent answers the first message that names it. Any agent but the Conductor can join. You seat agents in any thread; the Conductor only in a thread it delegated, and a team's lead only messages the members it has. Any other agent's call gets a 403.
- **Who gets a message.** A message that names no agent goes to the lead. One with agent pills goes only to the agents it names, and they all start at once, in the thread's one worktree. Each turn takes a slot from its own harness's limit, the way any thread does, so one agent may wait as Queued while another works; the thread has no limit of its own. An agent already working hears the message as a steer. A message sent to agents through the API or by the Conductor, with no `@name` in its text, names them on the line over it: To, then each agent's avatar and name. A team lead's message to its members shows the same way, under the lead's name. Naming the lead with a member sends to both. An `@name` in an agent's reply is plain text and seats no one. Once you type `@`, a line under the box says who the message goes to. The box reads "Reply to <lead>". The agent pill carries the agent's avatar in its color; a machine pill keeps its device icon.
- **Lanes.** The agents a message named answer in a lane each, under your message: the agent's avatar and state, its steps, its reply and the files it changed. Two lanes sit side by side where the transcript is wide enough. From three agents they stack, each folded to its latest line until you open it. The lanes stay lanes in the history. On a phone, the lanes are tabs, one per agent, and a tab with a flagged file carries a warning mark.
- **Collision flags.** When two agents edit the same file while both are at work, a flag above the lanes says "Both edited `thread/Composer.tsx`": the file with its folder, and the full path on hover. Each of the two is told which files the other changed: an agent on Claude Code or Codex hears it at once, mid-turn, and one on Cursor Agent at the start of its next turn. Omni counts the file edits its harnesses report, not files a shell command writes. A flag clears at the lead's next commit (your **Commit** in a thread a remote agent leads), or when you press **Dismiss**. Flags sync to your other Mac with the thread, and the Conductor sees the open ones in `get_thread`.
- **One checkpoint per message.** However many agents a message names, the turn's changes are one snapshot, taken when the message starts and closed when the last agent finishes.
- **Commits.** Only the lead commits, pushes or opens a PR. Members are told so, and a Claude Code member cannot run `git commit`, `git push` or `gh pr create`. A Cursor Cloud member works on a branch of its own in the cloud, with a diff and no PR. When it finishes, Omni asks the lead to pull that branch into the thread's branch. Its edits never raise a flag.
- **Stop** stops every agent in the thread. A message steers only the agents it goes to.
- **What a member reads.** Its first turn opens with a catch-up of the thread that a small model writes. Every turn after that opens with the messages since its last one that it did not write, without tool calls, cut to the carryover budget with a summary of anything older. The lead reads the members' replies the same way.
- **Remote agents.** Hermes and the agents on servers of your own sit in a thread like any other, lead one, or both, and talk only: local members change the files, and in a thread a remote agent leads you commit them with **Commit**. In a channel with **No thread excerpts to remote agents** on, a remote agent reads only the message addressed to it. See [Remote agents](crew.md#remote-agents).
- **The member list.** On desktop web and in the desktop app, the agents' avatars sit at the right of the thread header and open the list in a popover; on a phone they replace the status pill and open it in a sheet. A ring marks each agent that works, and the header shows no Working label. Each member has its state, its own run (harness, model and effort, starting from the agent's defaults, then the channel's, then Auto) and **Remove**. The composer's model pill changes only the lead's run. The quick-actions card shows a **Lead** row and a **Members** row.
- **Remove.** A member removed while it works finishes its turn first; messages waiting for it are dropped, and the "left" line follows its reply. Its replies stay. Seating it again starts a new session from a fresh catch-up. The lead cannot be removed.
- **Changes.** The Changes panel shows one diff for the whole thread, whoever wrote each line. While a flag is up, it sits over the diff with Dismiss, and the file's row carries a warning mark. Desktop web, phone web and the desktop app show it.
- **Questions and status.** A member's question card sits under its name, and the answer goes to that member's session. The thread's status mark is its busiest agent's: a question beats a failure, which beats working.
- **Moving the thread.** Handoff, Take over, Fork and Continue wait until every agent is idle, then every session moves together.
- **Read-only.** If the lead's agent is hidden or deleted, the thread goes read-only and the reply box says why.
- **Asks.** A thread no longer sends an Ask. Asks already in a thread keep their card, and an Ask from an older client seats the agent instead.
- The Conductor sees the members in `get_thread` and `list_threads`. It seats agents only in a thread it delegated, never in a #conductor thread: with `delegate_team`, with `members` on `delegate`, or with `agents` on `message_thread` ([Thread delegation](crew.md#thread-delegation)). The server refuses anything else with a 403, so the rule does not rest on its charter. You seat agents in #conductor threads and quick asks as anywhere. The routes are `POST /api/threads/<id>/members` with `{ agent }`, `DELETE /api/threads/<id>/members/<agent>` and `POST /api/threads/<id>/members/<agent>/run` with `{ harness, model, effort }`.

### Teams

A team is one thread with its lead and a member for each agent with a part. The Conductor makes one with `delegate_team`; teams made before that keep their tree of threads ([Thread delegation](crew.md#thread-delegation)).

- **The brief.** The thread's first message is the Conductor's brief to the lead, with every part under the agent that has it. An agent with two parts has one seat and both parts under it. The members join before it, with "Designer joined" lines.
- **Planning first.** The lead runs a turn on the brief, then gives each member its part with `message_members`, a tool only a team's lead gets, in its own team thread. It posts to members already seated and seats no one, and an `@name` in it stays plain text. The transcript shows each one as the lead's message, under the lead's name with To and the members it went to.
- **The members** start on their parts at once and work at the same time in the thread's one worktree, in lanes, as named agents do. Only the lead commits.
- **The wake.** Once every member the lead messaged has finished, Omni wakes the lead once with their replies ("All 3 members have finished."). A failed or stopped member counts as finished, and its part of the wake says so. While a member waits on your answer, the lead waits too and the thread shows Needs you. There is no time limit.
- **The report.** The crew report goes to the Conductor when that turn ends, not when the planning turn does. A team thread has one task id, `crew_prs` reports its one PR, and `crew_questions` names the member that asks.

## Reading a long thread

A thread opens on its newest messages. Scroll up to load earlier pages. A search hit opens the page with that message. If two loaded pages have a gap, use Show earlier or Show later to fill it. A large message or tool input may say **Trimmed for loading**, and Show all loads that row whole.

A message that starts a turn shows in the transcript as soon as you send it, above the thinking line. That covers the first message on a new thread, a reply sent while the thread is idle, and a queued message released after the turn it waited for. It shows even while the harness is still starting (hooks, MCP servers) or Omni is handing the turn to another machine.

While a turn runs, a thinking line stays up for the whole turn, tool calls included. It has the Omni mark, the label ("Thinking" or the agent's status) with a vermilion shimmer, and the time since your last message. It shows on desktop web, phone web, the desktop app and the iOS app. Reduce Motion stops the mark and the shimmer. A delegated thread's brief (its first message) folds to the first 6 lines, with Show more, when it is longer than 8 lines. Other long messages on desktop keep the character cut with Show all.

### Who wrote a reply

Each reply says which agent wrote it: the agent's avatar in a 24px gutter on the left, its name and the time beside it, and the reply under the name. Replies in a row from one agent share one head; your message, a report or a run switch starts the next. With **Show technical details** on, the harness and model it ran on show between the name and the time. A thread started as an agent shows that agent (its lead) on every reply, older threads included: Omni records the agent on each transcript row from now on, and rows from before that read as the lead's. The Conductor wears its channel's look until you give the Conductor agent an image or icon. A thread with no agent shows its replies without a head, as before. Desktop web, phone web and the desktop app show it; the iOS app gets it later.

Replies render as Markdown on desktop web, phone web and the desktop app. A `mermaid` code fence draws as a diagram in light and dark. A fence that fails to parse keeps its source visible. Wide diagrams scroll sideways on a phone.

Open a call under a step's **N actions** to read its output. Long output starts with a preview, then loads in chunks with Load more. A running Codex command can show its live tail. The other harnesses show output when the call ends. If the harness cut the output before saving it, loading more cannot recover it. The budgets and client rules are in [Thread history](../internals/thread-history.md).

### Find in a thread

Cmd+F (Ctrl+F off a Mac), or the search button in the thread header, opens a find bar over the transcript. On a phone it is **Find in thread** under Thread options (⋯). It finds text anywhere in the thread, not just the part on screen: your messages, replies, crew reports, errors, and every tool call's input and output, earlier pages included. Matching ignores case.

- The bar counts the matches, "3 of 12", and starts on the first one at or below the message you are reading, or the newest when you are at the bottom.
- Enter goes to the next match and Shift+Enter to the previous one, wrapping at either end. The arrows do the same.
- Each step loads the page that holds the match if needed, opens the steps card, the step's actions and the tool row it sits in, and scrolls it to the middle. Every match on screen is marked, and the current one is solid and underlined.
- Esc, or the close button, closes the bar and takes the marks off.
- One answer lists at most 1,000 matches. Past that the count reads "1000+".
- On a phone, tool calls and replies before a turn's last one live on the Steps screen, so a match there scrolls to its turn instead.
- The count comes from the stored text, so it can be higher than what the page draws: a link's address, Markdown syntax, or a long tool output past the part loaded so far. The bar still goes to that message.
- The iOS app has no find yet.

## Steps

An agent on a task with more than one stage posts its plan as 3 to 6 steps in plain words with Omni's `set_steps` tool, then moves the marker as each step starts or finishes. Claude Code, Codex and Cursor threads have it through the `omni-steps` MCP server, and their system prompt asks for it. When the agent posts no list, Omni uses the plan the harness keeps (Claude Code's todo list or its tasks, a Codex plan, Cursor's todos). With neither, Omni groups the turn's calls into plain phases such as "Searching the web" or "Looking through the files", ending in "Writing the answer". Hermes and Cursor Cloud threads have no Omni MCP servers, so they show phases. No step names a tool, a path or a command.

The steps take the place of the tool rows. A running turn shows its list under the transcript, above the thinking line: a status mark per step, "Now:" under the step it is on, and the threads a step handed work to. Each step's **N actions** opens the calls it made, with their output as before. A finished turn folds to one line ("3 steps · 12 actions") with **Show steps**. A turn that made no call shows no list, only the thinking line. On a phone the list sits in the turn the same way, and **N actions** opens the turn's Actions screen. The iOS app shows the running turn's list, and its actions under the turn. Steps are the agent's to move: you cannot tick one.

Calls to a connector or MCP server (Granola, Notion, Gmail, Google Calendar, Slack, Linear, Figma, GitHub, Shopify, Vercel and more) wear the app's own mark and name, as in Claude's apps. They stay in the transcript as one row per app: "Working on it" while a call runs, "Used Granola" after, and the chevron opens what each call sent and got back. The step it runs in reads "Now: Using Granola" with the app's mark, and the thread's quick card lists every connector the thread used under **Connectors**. A server Omni has no mark for gets a neutral plug and its own name, tidied ("Acme crm"). Omni's own tools wear the Omni ring inside the steps, and the browser, shell, file and search tools keep their usual look. The mapping is in `packages/shared/connectors.ts`.

While a thread runs, the step it is on goes out with the thread as one line: "Step 2 of 3 · Read the reviews" for a list, or the phase ("Searching the web"). The Inbox card shows it under the title on desktop web, the desktop app, phone web and the iOS app's Activity, and a question's notification on the desktop app names it ("Step 2 of 3 · Read the reviews · waiting on your answer in #volero"). Every machine reads it from the thread's own events, so a thread that runs on another machine shows the same line. How it is built: `packages/shared/steps.ts` and `apps/server/step-line.ts`.

## When the agent asks you

An agent can stop and ask you one to four multiple-choice questions with Omni's `ask_user_question` tool. Every Claude Code, Codex and Cursor thread has it through the `omni-ask` MCP server. Hermes and Cursor Cloud threads have no Omni MCP servers, so they don't. Omni turns off Claude Code's own AskUserQuestion, because nothing can answer it in a headless run.

- The questions show as a card in the thread, where the agent asked, and the thread shows in Needs you until you act, even while it runs. Pick an option (several on a multi-select question) or type your own under Other. Skip leaves a question to the agent's judgement.
- A card from a delegated thread (from `delegate` or `delegate_team`, at any depth) also shows at the end of every thread above it, under the asking thread's task id and title, which link to it. Needs you shows the top one, the thread you delegated from, and brings it back if you had marked it done. Answer on either card, on desktop web, the phone layout, the desktop app or the iOS app. The first answer wins and closes both. The asking thread keeps its card and the answer. The phone alert opens the thread you delegated from and names the thread that asked. The iPhone app keeps it quiet while either thread is on screen. A thread you continued (Continue on another harness) also shows the cards of the crew its earlier thread delegated, and Needs you and the alert point at the newest continuation instead of the earlier thread. The Conductor sees what its crew waits on with `crew_questions`.
- The turn waits on the call until you answer, for up to a day on Claude Code and Codex. Your answers go back as the call's result and the turn continues.
- If the call is gone by the time you answer (Omni restarted, you pressed Stop, or the harness gave up on it), your answers go to the thread as a message and it runs on them.
- A thread that runs on another machine takes the answer the same way, however it got there: sent there, delegated there by the Conductor, or moved there by a reply or Take over on that machine. While a turn runs there, the answer syncs to that machine and its waiting call returns. Between turns, Omni forwards the answer as a message to a thread that stays on that machine (one sent or delegated there, or a worktree thread); any other thread runs on your answer here, as it would on a reply. Answer on the hub, on the thread's card or the parent's. You do not need to open the other machine. If the other machine refuses the answer for a reason other than "already answered", the card shows that reason instead of waiting.
- Sending a message instead (steer or interrupt) closes the card as not answered, and the agent reads your message. A message queued for after the turn leaves the card open.

## Access levels

Channel settings > Access sets how much a channel's agents may do before they ask you ([ADR 0015](../adr/0015-access-levels.md)).

| Level | Runs without asking | Waits for your yes | Refused |
| --- | --- | --- | --- |
| Read only | Reading, searching, read-only commands | Nothing | Edits, other commands, account actions |
| Ask first | The same, plus edits in the thread's folder | Other commands and edits, account actions that send or change things | Nothing |
| Full access | Everything | Nothing | Nothing |

- Each connector (Gmail, Google Calendar, Slack, Notion, Google Drive, Granola, the browser) can have its own level, or Off, where even its reading tools are refused. One left at Same as channel follows the channel.
- A channel with no level runs at this computer's default: Full access on an install that already had threads, Ask first on a new one. The setting shows which.
- Ask first shows an approval card in the thread, on the same rails as a question card: Needs you, the alert, the phone and the other machine. Allow runs it once, Allow in this thread stops asking for that tool in the thread, Always allow for <agent> stops asking for that agent in the channel, and Don't allow (or a typed note) stops it and tells the agent. Channel settings lists the Always allowed tools with Remove.
- An agent's file can set `access: read` or `access: ask` to run stricter than its channel ([Crew](crew.md)).
- Per harness: Claude Code and Codex ask per call. Cursor Agent cannot ask, so Ask first runs as Read only there. Hermes and Cursor Cloud run elsewhere, so a channel below Full access refuses them. Connector levels other than the browser hold on Claude Code only: Codex and Cursor Agent run the MCP servers from your own Codex or Cursor config without asking Omni.
- Ask first still asks before an edit to a file a tool runs code from, such as `.git/`, `.claude/` or `.mcp.json`.
- Agents cannot change levels or grants: only you can, in Channel settings.

## What a thread gets

- **Worktree**: in a repo channel, its own git worktree on branch `omni/<id>`. If the agent checks out a branch of its own there (`git checkout -b feat/x`), the thread takes that branch as its own when the turn ends, so the PRs tab, PR marks and the PR watch find the PR opened from it. The thread does not take a detached HEAD or the default branch. The next message stops at Setup failed, and Retry switches a clean worktree back. Omni removes the worktree once nothing in it can be lost ([Known limits](limits.md)). While Omni prepares it, the thread shows each step (checkout, the channel's setup action if it has one, then the agent) with the setup's output and a Stop button ([Configuration](configuration.md#channel-actions)). When the channel's repo is not on this machine, the first step clones the channel's GitHub repo with this machine's `gh` (or `git`) login. It clones to the channel's path when Omni can create it here, and otherwise to `~/<repo name>`, or under the Repos folder in Settings > Workspace if you have set one there (its `~/code` default is not used). This machine's path map then records where the repo went. Threads that start together wait for one clone. Stop ends the wait at once, and the clone finishes in the background for Retry. A clone that fails, a folder in the way that is not the repo, or a path whose drive is not connected stops at Setup failed with the reason. Omni never clones into a folder that has files in it.
- **Base**: the commit that branch starts from. The new-thread composer shows the repo's current commit as the default ("From main · a1b2c3d") and lets you pick another branch or tag, or the remote default branch. Omni fetches the remote default first, and the repo's own checkout and branches never move. The thread keeps the commit it resolved, and the Changes tab compares against it, so a branch that moves later changes nothing. If the fetch fails (offline, no access), the thread stops at "Setup failed" with the reason and keeps your message, and Retry tries again. Threads started by a channel, agent or automation without a choice start from the repo's current commit, as before. Cursor Cloud threads, and Hermes threads from before remote agents, have no worktree here, so they have no base. A thread a remote agent leads gets its worktree and base like a local thread.
- **Browser**: the channel's persistent Chrome, where logins survive, shown live in the thread's Browser panel. You can click and type in it too.
- **Web tab** (desktop app only): your own browser, a web view in the app next to the Browser tab. Each channel keeps its own page, which reopens at the next launch. Logins are shared by every channel and stay on this machine. The agent can't see or drive it, so use the Browser tab for anything the agent should do. A browser and the phone have no Web tab, because a web page can't hold a web view of its own.
- **Terminal tab**: a real shell (PTY) in the thread's working directory.
- **Actions tab**: the channel's named actions (Theme preview, Theme check, Tests), each with a Run button, and the thread's last 20 runs. A run starts only when you press Run or Retry. It runs in the thread's checkout once Omni has verified it: a worktree thread's own worktree on its own branch, never the repo itself. A run shows Running, Succeeded, Failed or Stopped, the exit code, and the last 64 KB of its output. Stop ends the whole process group (SIGTERM, then SIGKILL after 5 seconds). Runs left running when Omni stopped show as Stopped. A running action keeps its worktree from cleanup, and starting an action after cleanup restores the thread's branch first. Hermes and Cursor Cloud threads can't run actions, because they have no checkout on this Mac. On the phone, open it from the thread's menu ([Configuration](configuration.md#channel-actions)).
- **Secrets**: global and channel secrets from the secret store, as env vars ([Configuration](configuration.md#secrets)).
- **Files**: anything the agent writes to its artifacts dir renders inline in the thread, in the thread panel's Files tab and in Files on the Artifacts page across channels. That page's Claude Artifacts switch lists your Artifacts on claude.ai ([Claude Artifacts](claude-artifacts.md)). Local threads also get an `html_render` tool (`omni-render` MCP) that shows a chart, diagram or mockup in the transcript above the reply. The render is sandboxed, sized to fit and drawn in Omni's theme. Hermes has no local MCP servers, so it cannot use it. When you ask an agent to "show me", "list out" or "visualize" something, its system prompt tells it to answer with `html_render` (cards, a table or a chart) rather than a wall of text. Omni saves the page under `artifacts/renders/`, and it stays in the Library like any file. A thread that delegated work, such as a Conductor thread, also lists the files and browser screenshots of every thread under it, teams and deeper delegations included, newest first under **From delegated threads**. On desktop they are in the panel's Artifacts tab and the Browser tab's screenshots. On a phone they are in the Details screen. Each one names the thread that made it and links to it, and a new one shows up while the parent is open. A page the parent lists itself shows once, as its own.
- **Published artifacts**: a page a Claude Code thread publishes to claude.ai with its Artifact tool shows as a card in the thread, linked to its local file. The channel's pages go into later threads' system prompt, so an update lands at the same URL. "Check comments" (or the `artifact-comments` automation) hands a page's comments back to the thread that made it.
- **Pull requests**: in a repo channel and each thread's PRs tab, checks, diff and merge. Merge works in place from the panel's Merge button, and the phone PR screen keeps its merge slide. The Pull requests page (`#/prs`, and the phone's PRs tab) lists every channel's PRs with search, sort and filters, grouped into Authored, Review requested and Others. Threads whose branch has an open or merged PR get a PR icon in the thread list. A GitHub PR link anywhere in Omni (a reply, a card, a list row, or an agent's HTML page in the desktop app) opens that PR's page in Omni when one of your channels has its repo. A PR from another repo still opens on GitHub, and so does a Cmd- or Ctrl-click, a middle click or the PR page's GitHub button. In a browser tab, a link inside an agent's HTML page still opens GitHub, because the page's sandbox hides the click from Omni. The iOS app has no PR page for a channel, so its links open GitHub.

How Omni launches the process behind a thread: [Architecture overview](../internals/overview.md#how-a-thread-runs).

## Watch PR

A thread with an open PR can watch its checks and its reviews. Start it with **Watch PR** in the thread panel's PRs tab (on the phone, the PR screen) or the Conductor's `watch_pr` tool. Omni polls GitHub itself, so no client needs to be open, and a poll with no changes costs no agent turn.

- A check that fails on the PR head wakes the thread once, with the head commit, the failing checks and the tail of each GitHub Actions log. If the same check fails again on the same head after a re-run, it does not wake the thread again. A failure on a new head does.
- New review feedback from someone else wakes it too: a review with a comment or a change request, an inline comment, or a conversation comment. One wake carries everything new since the last poll, with each author, a link, the head the comment was written on and an excerpt. The first eight come with their text and the rest by link. Only feedback written after the watch started counts.
- Your own comments (from the account `gh` is signed in as) never wake it, so the agent replying on the PR cannot start a loop. Omni ignores comments from people with no history in the repo; bots count. A person editing a comment to new words wakes it once more. A bot editing its own comment does not, and neither does an edit back to words it already woke for.
- Omni quotes comment text to the agent as input to weigh, not as instructions from you.
- Omni saves the wake before it sends it, like any queued message. A wake saved before a restart waits in the thread for Resume. A thread this Mac cannot run (it runs on your other Mac, or its worktree is not ready) also gets the wake held for Resume.
- Polls come every minute while checks run and slow to every 15 minutes while nothing changes. GitHub errors back off, and five in a row stop the watch. A rate limit pauses every watch for 15 minutes without counting as an error.
- A watch ends when you stop it, the PR merges or closes, or the thread is archived. It also ends after it has woken the thread five times, or three times for review comments alone with no failing check in the wake. The PRs tab says which. Watch PR starts it again with fresh budgets. Starting a watch that is already running changes nothing.
- Watches live on the Mac that started them and do not sync.

## Auto-merge

An open PR can merge by itself once its required checks and reviews pass (`gh pr merge --auto`), so you can turn it on from the phone and walk away. The **Auto-merge** row shows whether it is on, with which method and who turned it on, and turns it on or off. It is on the desktop PR page's merge card, beside the card's headline, uses the method picked on the card, and the card's note says what it does and who turned it on while it is on. It is also on the phone web PR screen and in the iOS app, where a tap shows the same confirm slide as a merge.

- Only a paired device can turn it on. The server refuses a request from the install token or a thread's own token, which agents hold, so the Conductor's `set_auto_merge` tool can only read it or turn it off. A thread's token cannot pair a device either, so an agent cannot get a session of its own.
- It uses the repo's merge method: the one asked for when the repo allows it, otherwise the first of squash, merge and rebase that the repo allows.
- A repo with auto-merge turned off in its GitHub settings refuses, and gh's message shows in place.
- A PR that can already merge may merge at once.
- The state lives on GitHub, so every Mac and client sees the same.

## Merge risk

Omni rates each PR a builder thread opens in Omni's own repo, so you can tell which PRs are safe to merge without reading them. It rates only: it never merges, never turns on auto-merge and blocks nothing.

- A fresh Claude call with no tools reads the PR's title, body and diff and nothing else, and rates five areas good, decent or poor: Alignment, Impact, Verification, Rollback cost and Error detection. The rubric is `.agents/skills/merge-risk/SKILL.md` as `main` has it on GitHub, fetched before each rating, so a PR cannot loosen the rules it is rated by.
- Code, not the model, turns the ratings into low, medium or high, with the weights and thresholds the rubric lists (`apps/server/merge-risk/level.ts`).
- The PR gets one comment, `**Merge risk: <level>**` with a line for each area not rated good, and one label. `merge-ready` means an `omni/` branch with every area good. Anything else, including a low rating with one decent area, gets `needs-<your first name>` from the name in Settings > General (`needs-review` with no name set). A rating call that fails twice leaves a "not rated" comment and that same label.
- A new push is rated again once the builder's turn has ended: the same comment is edited and the label swapped, and `merge-ready` comes off while the new push waits for its rating.
- Only open, non-draft PRs whose branch belongs to a builder thread count, polled at the pace of event automations (`OMNI_AUTOMATION_POLL_SECONDS`). With sync on, only the machine that runs automations rates. Until `main` has the rubric, nothing is rated. `OMNI_MERGE_RISK=0` turns it off.

## Send to Grok Bot

Send to Grok Bot in the thread's menu (the header's ⋯ or a right-click) sends the title and the messages. On a phone, Thread options has the same action. Omni sends the channel id and the thread id as context. The Conductor tool is `send_to_grok_bot`. The action shows only on a server with a Grok Bot webhook URL. For where the webhook URL and Authorization value go, see [Configuration](configuration.md#grok-bot).

To send a new message straight to Grok Bot, without a thread running here first, pick **Grok Bot** in the new-thread composer's Machine chip ("To Grok Bot"). This works on desktop web, the phone and the desktop app. Send posts your text to the same webhook, with the channel id as context. No thread starts in Omni, and Grok Bot's reply comes back in Grok Bot.

- On success the composer empties and says Sent to Grok Bot.
- If the webhook refuses the message, the composer keeps your text and shows Grok Bot's error: a missing secret, the HTTP status, or why it could not be reached.
- The model, base and agent pickers hide while Grok Bot is picked.
- Grok Bot takes text only, so the composer won't send while a file is attached and asks you to remove it.
- Grok Bot is never a default, so Settings > Run new threads on doesn't list it.
- On a server without the webhook URL, the row is listed but disabled when other machines show the chip. On a single machine the chip stays hidden.
