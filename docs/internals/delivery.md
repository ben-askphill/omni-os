# Delivery contract

What Omni promises about a message, a wake or a Stop once it has said yes to it, wherever the thread runs. The local path keeps these promises, and so does a message, crew report, limit action or Stop sent to the machine running a thread (#398), a wake for a thread another machine holds (#399), and a resume whose session could not be brought here (#400). A path found not to keep them gets an expected-fail test that flips when its fix lands.

## The contract

1. **Accepted means an outcome.** Once a client hears "accepted", the message ends in a terminal state someone can see: delivered, dropped, discarded or cancelled, or parked for Ben to decide (`recovered`, `uncertain`). No cap, age limit or restart removes it silently. Locally that is `message_requests` (`apps/server/db/repos/requests.ts`), written before the answer and moved through its states by the runner. Across machines it is a remote command (`apps/server/db/repos/remote-commands.ts`): one synced row per forwarded message, crew report, limit action and Stop, written before the sender answers "accepted". The holder answers it `accepted` or `rejected` with why; one it finds past its deadline (24 hours, 2 minutes for a Stop) it marks `expired`, and the sender expires its own a minute after that when no holder answered. A row only moves forward, so an acceptance beats an expiry from either side. The sender writes a rejected or expired outcome into the transcript (`apps/server/remote-outcomes.ts`): a message or report as not delivered with the reason, a Stop or limit action as an error line.
2. **One owner, checked where delivery happens.** At any moment one machine runs a thread: its assignment (`apps/server/db/repos/assignments.ts`, [ADR 0005](../adr/0005-one-execution-owner.md)), which a turn, a pickup or the hub's routing claims, and which syncs by generation. Ben's messages, Stop, run switches, crew reports, PR-watch wakes and limit resumes all go to that owner, or wait for Resume. The check is at the delivery boundary (`apps/server/sync/guard.ts` `turnBlocked` and `wakeBlocked`, applied in `runner/queue.ts wake`), not repeated in each caller, so a new path cannot skip it. A process that started a turn on an earlier generation is stale: it gets no more messages and its turn is stopped at the next sync. A thread on a remote provider (Hermes, Cursor Cloud) still has an owner machine, the one that talks to the provider. A run switch, a handoff or Take over and a Continue are transitions (`apps/server/transition.ts`, [transitions](transitions.md)): each is refused at that same boundary, whichever route asks for it.
3. **A resume starts from the latest turns.** A process resumes a thread only on a session that holds every turn the previous owner synced. When the session cannot be brought here (`beforeResume` in `apps/server/sync/files.ts` returns `failed` or `timed-out`), `runner/spawn.ts` does not start the turn on the stale copy: its messages wait for Resume, the thread's `resume_blocked` says why on every client, and the transcript gets an error row. Ben tries again (`POST /api/threads/:id/session/retry`) or starts with fresh context (`POST /api/threads/:id/session/fresh`, `apps/server/runner/fresh-context.ts`): a new session that reads the thread from Omni's synced transcript, as a harness switch does. The Conductor has both as `recover_thread_session`. A fresh session, and Hermes or Cursor Cloud, which keep their session with the provider, never wait on the download.
4. **Stop is a command like any other.** It has an id and a durable receipt, and it reaches the turn that was running when Ben pressed it, not a later one. Across machines a Stop is a remote command with a two-minute deadline: the holder stops the turn it finds running and answers `accepted`, or answers `rejected` when nothing runs. It does not yet name the turn Ben pressed it on, so a turn that starts within those two minutes can be the one stopped.

## Where it does not hold yet

None known. A gap found later gets a row here: what breaks, where, its test and the issue that fixes it.

## The expected-fail tests

- Each is a vitest `it.fails`: it passes while the gap is there, so CI stays green.
- It asserts the contract, not today's behaviour, so the fix makes the assertions pass and `it.fails` then reports a failure. The fixing PR turns it into a plain `it` and moves its row out of the table above.
- The gap 1 test (`apps/server/tests/delivery-gap-run-on.test.ts`) is a plain `it` since #398: it checks each reply's command on both machines, the holder's expiry of a day-old one, the hub's own expiry when the holder never answers, and a rejected Stop.
- The gap 2 test (`apps/server/tests/delivery-gap-pr-watch.test.ts`) is a plain `it` since #399: a PR watch polled here for a thread another machine holds between turns wakes nothing here and parks the wake for Resume.
- The gap 3 test (`apps/server/tests/delivery-gap-stale-resume.test.ts`) is a plain `it` since #400: a message sent while the session download fails resumes nothing and waits for Resume with the reason on the thread. Its neighbours check Try again, which resumes once the download works, and start with fresh context, which starts a new session that reads the thread.
